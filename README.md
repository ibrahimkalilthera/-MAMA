# MAMA THERA Finance Suite

Application de gestion financière scolaire (élèves, parents, paiements, dépenses, paie, audit) — React 19 + TypeScript strict + Vite 6 + Tailwind 4, backend Supabase (Auth + RLS), i18n fr/en, 6 thèmes, file d'écriture offline pour le terrain (Bamako).

> Documentation d'historique et d'architecture détaillée : voir `DEVELOPMENT_HISTORY.md`.

## Démarrage rapide

**Prérequis** : Node.js **22** (pinné dans `.nvmrc`) — **aucun gestionnaire de version à installer**. Le projet provisionne lui-même le runtime qu'il épingle : `npm run setup:node` (aussi lancé en douceur par `npm install`), et **toutes** les entrées du projet passent par `scripts/with-pinned-node.mjs`, qui bascule sur ce runtime : les hooks git, les gates (`npm run lint`, `npm run quality`) et les commandes du quotidien (`npm run dev`, `build`, `preview`, `electron:ui`) — celles-ci par le mode `--bin`, qui exécute l'entrée que le paquet déclare lui-même (`vite`), donc **plus aucune commande ne résout son outil par `PATH`**. Ce pin n'est **plus** injecté dans la variable `PATH` : le lanceur écrit `node`, `npm` et `npx` dans `node_modules/.bin`, le dossier que npm met **déjà en tête** pour chaque script (`eslint`, `tsc` s'y résolvent ainsi) — le pin devient structurel au lieu d'être réécrit dans l'environnement, et une recherche PATH (`where npm`) ne peut plus tomber sur un de nos wrappers en le prenant pour l'npm de la machine. Sur une machine déjà en 22 (comme la CI), la bascule est un no-op : rien à télécharger. Pour un **terminal** sur ce runtime : `npm run shell` (ou, dans un terminal déjà ouvert, `export PATH="$(npm run --silent shell -- --print):$PATH"`).

> ⚠️ **Version de Node — pourquoi 22 ?**
> Les tests utilisent `mock.module()` avec l'option `namedExports`, **seule API disponible sur Node 22** (celle de la CI). Sur Node ≥ 25, cette option est dépréciée au profit de `exports` (warning `DeprecationWarning` local). Node 23/24 fonctionnent avec un warning ; rester sur 22 garantit la parité CI/local. Migrer vers `exports` seulement quand Node 22 EOL et que la CI passe sur Node ≥ 25.

```bash
# 1. Installer les dépendances (npm uniquement — package-lock.json est la source de vérité)
npm install

# 2. Configurer l'environnement
cp .env.example .env
# puis remplir VITE_SUPABASE_URL, VITE_SUPABASE_ANON_KEY (obligatoires)

# 3. Lancer le serveur de développement
npm run dev            # http://localhost:3000

# 4. Vérifier la qualité avant de commit
npm run quality        # lint (0 warning) + tests + audit de contraste
```

```bash
npx supabase migrations up   # ou via le dashboard Supabase
npm run seed                 # données de démo (env .env — refusé sans VITE_APP_ENV dev|staging)
```

> Les helpers `_update_role.cjs`, `debug-auth.cjs`, `scripts/audit-user-profiles.mjs`
> restants sont des scripts ponctuels d'une époque où le schéma n'était pas
> versionné — certains embarquent des identifiants de production, ne les
> exécutez pas sur la base courante ; l'application du schéma se fait
> exclusivement via le CLI/Dashboard Supabase sur `supabase/migrations/`.

RLS activé sur toutes les tables, politiques par rôle (`admin` / `staff` / `dev` / `general_manager` / `econome`).

**Les trois classes CR (crèche / jardin d'enfants) sont écrites des deux côtés, et un test le verrouille.** « Ajouter CR » enrôle un enfant dans la crèche : c'est le **même** formulaire que « Ajouter un Élève » (même parent, mêmes frais, même reçu, même fiche), seule la liste de classes change — Petit, Moyen, Grand, dans le cycle **Maternelle / Jardin d'Enfants** que les modales de classe connaissent déjà (PS / MS / GS). Les trois codes vivent dans `DEFAULT_SCHOOL_CLASSES` (l'app les connaît **sans réseau**, le filtre de classes les propose, et le formulaire CR n'offre **que** ce cycle) **et** dans `custom_classes` (migration `20260914000002`) pour qu'un poste dont le build ne les embarque pas encore — une application installée sur une version antérieure — les voie quand même à la connexion ; la fusion `useClasses.availableClasses` dédoublonne par code, donc la ligne de base ne crée pas de doublon visible. `tests/nursery-classes.test.ts` relit les **deux** sources et échoue à la première divergence, dans un sens comme dans l'autre (une classe déclarée mais jamais semée, une classe semée que l'app ne déclare pas).

**La base hébergée est comparée aux migrations à chaque déploiement** — parce que le 14/09 elle ne l'était par personne. `staff.category` a été écrite dans le code **avant** d'exister dans la base : PostgREST valide les colonnes demandées **avant** d'appliquer la RLS, donc `select=category` rendait `400` et **tout AJOUT de membre** aurait été refusé — pendant que la chaîne qualité et le déploiement restaient verts (la chaîne ne lit que le dépôt, les migrations s'appliquent à la main, et rien ne comparait les deux). C'est la même famille que le compte dev disparu la veille : ce qui manquait n'était écrit dans **aucun** fichier.

`npm run check:hosted-schema` **déduit** donc le schéma attendu de `supabase/migrations/` — une deuxième liste écrite à la main aurait dérivé de la première, et c'est exactement cette dérive-là qu'il existe pour attraper — et le confronte à ce que la base **répond** : `GET /rest/v1/<table>?select=<colonnes>&limit=0`, avec la clé **anon publique** (celle qui est embarquée dans le client). Aucun secret, aucune écriture, aucun compte à créer : il ne lit pas une ligne, il ne fait que nommer des colonnes. **Deux formes pour la même absence**, et les deux ont été mesurées sur la base réelle : `PGRST204` (« Could not find the 'x' column of 'y' ») quand c'est le **cache de schéma** de PostgREST qui refuse, `42703` (« column y.x does not exist ») quand c'est PostgreSQL — ne reconnaître que la première aurait classé un vrai retard en « invérifiable », c'est-à-dire en **exit 2 au lieu du 1 qui le nomme**. Un contrôle qui ne peut pas regarder (zéro migration lue, clé absente, table sans colonne) sort en **2** : « je n'ai pas pu regarder » n'est jamais un vert.

**C'est la 4ᵉ porte de `deploy.yml`** (à côté de la sonde anon RLS, avant `npm ci` et le build), et sa sémantique est **volontairement différente** des portes 2 et 3 : une base **EN RETARD** est un défaut nommé et rend le run **ROUGE** — un déploiement dont le schéma manque casse un **AJOUT**, pas une lecture — tandis que « je n'ai pas pu regarder » reste **neutre** (78). Dans les deux cas, rien n'est déployé. Mesuré les trois chemins en vrai : **14 tables et 131 colonnes** toutes présentes (sortie 0) sur la base partagée avec la seule clé anon ; `❌ la base hébergée est EN RETARD` nommant `staff.probe_absent_column` (sortie 1) sur une migration non appliquée ; sortie 2 sur une base injoignable — et le pas de CI rejoué pour les trois codes (0→0, **1→1**, 2→78).

**Un membre du personnel porte sa SORTE en base** : `staff.category` (`employee` / `technique` / `admin`, migration `20260914000000`) est écrite par le flux qui crée le membre — « Ajouter un Employé », « Ajouter un Membre du Centre T et P », « Ajouter un Membre de l'Administration » — et c'est elle, jamais le texte du poste, qui décide du **document** téléchargé (fiche de paiement, fiche T et P, bulletin de paie) et du bac du répertoire. Les lignes antérieures à la colonne sont relues par leur poste une seule fois (`staffCategory()`, `lib/adminPositions.ts`) ; une position reformulée ne change donc plus la sorte d'un membre. Et une écriture qui n'a **rien** touché (cible écartée par une policy RLS : PostgREST répond alors 200 avec un corps vide) échoue en le disant au lieu d'annoncer « Employé supprimé ». **Cette règle vaut maintenant pour TOUTE la couche d'écriture** — élèves, parents, dépenses (générales et fournisseur), tâches, classes : chaque suppression demande **ce qui a été supprimé** (`.select('id')`, donc PostgREST rend les lignes réellement parties) et un retour vide est un **échec signalé**, jamais un succès muet.

C'est exactement ce qui manquait aux **élèves** et aux **parents**, et les deux ont leur propre table sur la base partagée (`students`, `parents` — 27 et 9 colonnes, vérifiées par `check:hosted-schema`). La policy `Admin delete students` / `Admin delete parents` limite la suppression aux **administrateurs** : un utilisateur connecté non administrateur recevait donc **200 avec 0 ligne**, l'écran annonçait « Élève supprimé(e) » au-dessus d'une ligne toujours en base, et les **paiements** de l'élève restaient aussi (la cascade ne se déclenche que sur une ligne réellement supprimée). **Mesuré sur la base partagée le 2026-09-14, par le canal de l'app** (compte jetable promu admin, **login réel** par la clé anon, rien laissé derrière) : élève `201` puis relu `200`, parent `201` puis relu `200`, `DELETE` d'un administrateur → **1 ligne rendue** (vraiment supprimé) ; et la **même** requête **sans session** rend `200 · 0 ligne` avec la ligne toujours vivante — le cas que le code honnête attrape. `tests/dataops-write-honesty.test.ts` (12 cas) lit toute la couche d'écriture et refuse une suppression qui ne demande pas ce qu'elle a supprimé (`maskComments` : la prose qui cite la règle n'est pas la règle) — vérifié en remettant une suppression muette, le contrôle nomme le fichier.

**Et l'action de suppression n'existe plus là où la base la refuse.** Dire l'échec ne suffisait pas : l'utilisateur voyait le bouton, le pressait, et recevait un refus. La règle vit à un seul endroit (`src/lib/deleteRights.ts`) — les rôles de `public.is_admin()` (`admin`, `dev`) et les **huit** tables dont la suppression leur est réservée (`students`, `parents`, `payments`, `staff`, `salary_payments`, `expenses`, `vendor_expenses`, `user_profiles` ; les tâches et les classes n'y sont **pas** — leurs policies laissent passer tout compte connecté, et les inclure aurait caché un bouton légitime). `useAuth.isAdmin` en dérive, `App.tsx` en dérive `canDelete`, et le bouton n'est **pas rendu** — absent du HTML, pas grisé : un bouton désactivé laisserait croire à un problème de droits temporaire, un bouton absent dit exactement ce que la base dit. Mesuré sur le rendu réel (`tests/delete-rights.test.ts`, 10 cas) : élèves, parents et personnel affichent la ligne **et** l'action pour `admin`/`dev`, la ligne reste mais l'action **disparaît** pour `staff`. La non-divergence avec la base est verrouillée **dans les deux sens** : le test lit la migration RLS, extrait les rôles de `public.is_admin()` et les tables de policy `FOR DELETE USING (public.is_admin())`, et les compare aux deux listes du code — un rôle ou une table resserré d'un seul côté rouvrirait (ou fermerait) un bouton que la base ne suit pas ; un cas anti-vacuité exige que la migration soit réellement lue, sinon un parseur aveugle rendrait un vert parfait sur rien. Le rôle est lu sans naïveté (casse et espaces tolérés, **tout ce qui n'est pas reconnu est refusé** : `null`, `''`, `'root'`, une faute de frappe).

## Tests

```bash
npm test                    # toute la suite (~60 s)
node --import tsx --experimental-test-module-mocks --test tests/payments.test.tsx   # une seule suite
```

- Framework : `node:test` natif + `tsx`, rendu DOM via `happy-dom`
- Mocks de module : une suite n'écrit plus le nom de l'option — il **dépend du runtime** (`namedExports` jusqu'à Node 22 ; `exports` à partir de 24.20 / 25.9, où l'ancien nom est déprécié). `tests/module-mock.ts` **sonde** la capacité du Node qui exécute la suite et rend la forme qu'il lit ; une suite écrit `mockModule('node:fs', { … })`. Le nom n'est recopié nulle part (testé), et un cas **vivo** prouve que la forme choisie mocke pour de vrai — sur Node 22, l'autre nom enregistre un mock qui ne remplace rien. Mesuré sur deux runtimes réels : **124/124** et **7/7** verts sur Node 26.8.1 **sans un seul `DeprecationWarning`**, autant sur le Node 22 du pin.
- Garde-fous testés : file offline (replay FIFO), PDF (tampon, i18n), contraste calculé ≥ 4,5:1, focus traps, ARIA, contrats de props (`MainViewsProps`), RLS anon (CI Supabase local)
- Garde-fou des garde-fous : `scripts/check-test-integrity.mjs` refuse une suite qui ne peut pas échouer — `mock.module()`/`mockModule()` que personne ne charge (vérifié contre la fermeture d'imports réelle), mock vide, branche d'OS asserée sans injecter `platform`, suite sautée selon la plateforme, fichier sans assertion. Un saut légitime (le shim `git.cmd` a besoin d'un vrai `cmd.exe`) se **déclare** en commentaire (`// @platform-skip : …`, `// @platform-guard : …`) et le gate l'affiche dans son résumé à chaque run — la couverture manquante reste visible au lieu de compter comme des tests verts.

## Chaîne qualité (pre-commit + CI)

Le hook husky `pre-commit` et le workflow `perf-guard` exécutent la même chaîne :
**lint (0 warning, guards) → tests → audit npm → Lighthouse ≥ 0,60 → audit contraste (6 thèmes × 8 overlays)**.
`deploy.yml` ne déploie que si la porte qualité est verte sur le commit exact.

Et « la même chaîne » se lit au sens strict : le job CI lance **`npm run lint`**, la commande du poste telle quelle, jamais un sous-ensemble recopié. Il exécutait auparavant `npx eslint .` + `npx tsc` + deux gardes et sautait donc en silence stylelint, les sélecteurs CSS, emoji, i18n, les dates Windows, le budget de lignes, les gardes du harnais de tests et le contrôle du snapshot SQL.

Cette fois la règle n'est plus une convention pour le seul job `lint` : **`scripts/check-ci-commands.mjs`** compare **chaque workflow** à `package.json` et refuse toute étape qui **recopie** une commande existante au lieu de l'appeler par son nom. Trois formes, un remède chacune : **recopie exacte** (`node scripts/theme-contrast-audit.mjs` alors que `check:contrast` EST cette commande — non allowlistable), **maillon de chaîne** (un `&&` d'un script, comme `check-node-version.mjs` en tête de `lint:chain` : modifier le script laisserait la CI derrière), **outil piloté à la main** (`npx eslint .` avec ses propres drapeaux — c'est le drapeau qui dérive). Le remède nomme **l'entrée publique** remontée par les liens `--npm` (`npm run lint`, pas `lint:chain`, qui sauterait le runtime épinglé), et chaque exception vit dans une allowlist **motivée** dont une entrée qui ne correspond plus fait échouer le gate. Le dépôt est en 0 recopie : les 4 pas de parité Node sont grandfathered (chaque job doit prouver le majeur dans **son** log), et le contraste est appelé par son nom — c'était la recopie que le premier run a trouvée. Zéro workflow ou zéro commande lue est une **erreur**, pas un vert.

La chaîne `lint` commence par `scripts/check-node-version.mjs` : elle vérifie que le majeur **réellement exécuté** est celui de `.nvmrc` (donc de la CI). Les points d'entrée pinnent ce runtime (`scripts/with-pinned-node.mjs`) et le gate le contrôle — pinner sans vérifier laisserait passer un PATH détourné, et vérifier sans pinner bloquait tout poste sans gestionnaire de version. Un « vert » local sur un autre majeur ne doit plus jamais passer pour une validation — c'est exactement ce qui a bloqué deux déploiements (voir « Version de Node » ci-dessus). Côté CI, l'audit de contraste **ne demande plus aucun secret** : il construit le bundle contre un hôte Supabase factice et répond à toutes ses requêtes depuis un jeu de données figé (`scripts/lib/audit-fixtures.mjs`), grant de mot de passe compris — le formulaire de login est donc rempli pour de vrai, et la session stockée est celle que l'audit a fournie. Le gate tourne donc **à l'identique** sur un push, une PR interne, une PR **Dependabot** ou une PR de fork, avec exactement les mêmes données à chaque run (une couleur ne doit pas changer de verdict parce qu'une ligne a été ajoutée en base). Pour auditer un vrai backend : `AUDIT_FIXTURES=0 AUDIT_EMAIL=… AUDIT_PASSWORD=… npm run check:contrast`. Deux réglages rendent le jeu figé **utilisable** et non seulement présent : toutes ses lignes portent `FIXTURE_ACADEMIC_YEAR`, épinglée sur l'année par défaut de `YearProvider` par un test (une vue filtrée par année vide ses lignes **en silence** quand les deux dérivent — c'est ainsi que « Fiche Élève » est restée non mesurée dans les six thèmes), et l'étape « Fiche Élève » **échoue** désormais si le tableau est vide au lieu d'être déclarée « non applicable ». La règle est générale : comme le jeu de fixtures est figé, chaque surface auditée y a toujours son déclencheur — **sous fixtures, « non applicable » est donc un KO** (déclencheur perdu), pas une variation de données ; sous un vrai backend (`AUDIT_FIXTURES=0`) l'absence de déclencheur reste légitime, mais elle est **imprimée** dans le rapport. Une surface que personne n'a mesurée doit être une ligne, jamais un silence. **Et une surface que le thème ne peint pas en sombre garde sa propre couleur de texte** : le fond **résolu** sous chaque thème sombre est le critère (une surface encore claire n'a pas été repeinte), donc le texte posé dessus doit passer AA 4,5:1 — un futur panneau clair au texte blanc échoue tout seul, sans liste à tenir, et `text-white` (sans nuance chiffrée) est enfin lu par un scanner. La règle est vérifiée sur l'arbre réel **et** sur une fixture injectée qui prouve qu'elle mord.

Une machine ne peut prouver que **son** layout npm — et c'est précisément ce qu'un test qui fabrique une arborescence ne peut pas faire : un arbre inventé valide la liste des candidats, jamais ce que le runner a installé. C'est ainsi que `resolveNpmCliJs` était vert ici et levait sur ubuntu. D'où un job **`node-layouts`** en matrice (`ubuntu-latest` + `windows-latest`, `fail-fast: false`) qui exécute **`npm run check:node-layout`** sur un vrai runner : il résout npm, vérifie que le fichier existe, l'**exécute** (`node npm-cli.js --version` doit rendre une version — un chemin qui existe n'est pas npm), et exige que la résolution tombe sur le npm **de la machine**, dans le layout de sa plateforme. Il ne fait aucun `npm ci` — ce qu'il vérifie est justement l'installation du runner, pas la nôtre — et il sort en rouge avec le chemin trouvé, le chemin attendu et la source quand les deux divergent.

Le hook peut aussi mourir **avant** de tourner : la panique de fork msys frappe le `sh` que git utilise pour lancer un hook (contexte et procédure dans `DEVELOPMENT_HISTORY.md`). `scripts/git-shim.cmd`, installé comme `git.cmd` sur le PATH utilisateur par `node scripts/install-git-shim.mjs`, intercepte nativement `git commit`, `git push`, **`git pull`** et **`git rebase`** et les rejoue via `scripts/git-retry.mjs` : retry **uniquement** sur signature de panique (un conflit, une branche divergée ou un push rejeté ressortent au premier essai avec le code de git), purge des `node.exe` orphelins qui entretiennent la panique, watchdog qui tue l'arbre entier. `pull` et `rebase` sont couverts pour deux raisons cumulées — ils lancent aussi des hooks (`post-merge`, `post-rewrite`, `pre-rebase`) et, étant longs et *stateful*, ce sont eux que la panique interrompt au pire moment : un rejeu coupé en plein vol laisse un état à nettoyer à la main. Git Bash et les outils node qui spawn `git` sans shell ignorent le shim (ils trouvent `git.exe`) : y garder `npm run git:retry -- …`.

**La chaîne purge ses propres orphelins — en lignée, et une mesure a corrigé le modèle.** Le déclencheur documenté de la panique est un `node.exe` orphelin laissé par un timeout dur. Mesuré sur ce poste, ce n'est pas ainsi qu'un arbre node fuit : un enfant node **non détaché** meurt avec son parent — 9 descendants sur 9 disparus en 500 ms après un `taskkill /PID <racine> /F` (sans `/T`), et de même avec `Stop-Process -Force` (comportement Windows documenté de Node : seul `detached: true` laisse un enfant survivre ; libuv l'obtient par un job object). L'orphelin atteignable est donc le **détaché** — sonde réelle : 1 descendant sur 4 survit à la mort de sa racine, et cette purge l'a tué — ou un **wrapper dont le parent non-node est mort**, produit de la panique elle-même : le `sh.exe` qui lance un hook git meurt, le node qu'il a déjà lancé continue et porte alors la chaîne entière. Ce second cas est *périmé par définition* (son pid a disparu depuis longtemps) et reste le travail du filtre par ligne de commande de `scripts/git-retry.mjs`, qui ne matche que ces wrappers. La purge de sortie, elle, est en **lignée** : elle ne tue que ce que cette exécution a créé, identifié par pid **et** horodatage de création — un pid recyclé porte un autre horodatage et est ignoré, donc un `node.exe` étranger (serveur de dev, chaîne d'un autre agent) ne peut pas y passer — et elle tourne sur **tous** les chemins de sortie (fin normale, étape en échec, `SIGINT`/`SIGTERM`). Le garde détaché couvre le seul chemin inatteignable (kill externe) en relevant les descendants **pendant** que la chaîne vit, ce qui authentifie chaque cible. Une purge qui n'a pas pu s'exécuter est comptée comme un **échec**, jamais présentée comme « rien à tuer ». Chaque purge est journalisée, **zéros compris** — sans dénominateur, « à quelle fréquence la panique arrive-t-elle ? » reste une anecdote — Pour voir cet état **avant** d'agir, `npm run orphans:doctor` (lecture seule : il ne tue rien, il nomme la commande qui le ferait). Et le chemin où la panique frappe vraiment — la commande git — est mesuré lui aussi : chaque `--sweep`/`--sweep-all` écrit son compteur (nombre tué, commande git, **avant la 1re tentative ou après une panique**), et chaque fork-panic détecté par le wrapper écrit **la panique elle-même** (commande git, code de sortie, tentative). C'est la seule façon de répondre à « à quelle fréquence ? » : une panique sans `--sweep` ne purge rien, donc compter les purges ne mesure jamais les paniques. `npm run orphans:report` lit ce journal (totaux par origine, paniques par commande git, fenêtre, dernières entrées ; un taux n'est affiché qu'au-delà d'un jour, sinon la fenêtre qui le porte est trop courte pour vouloir dire quelque chose).

**La chaîne ne cherche plus ses outils dans `PATH`.** Chaque étape découpe son script de `package.json` en maillons et les exécute **explicitement** — `node <abs>/node_modules/eslint/bin/eslint.js`, `tsc` par l'entrée déclarée par `typescript`, `vite` par la sienne (`scripts/lib/chain-links.mjs`) — au lieu de `npm run <script>`, qui lance un shell et laisse ce shell résoudre `node`, `eslint`, `tsc` et `stylelint` selon l'**ordre** du `PATH`. L'entrée est **lue** dans le champ `bin` du paquet installé : le chemin explicite et celui qu'npm aurait utilisé sont donc le **même fichier**, et le nom de commande n'est jamais supposé être le nom du paquet (`tsc` est déclaré par `typescript` — une table d'alias serait une seconde définition de ce qu'npm sait déjà). Un maillon non résoluble **échoue** : il n'est jamais rendu au `PATH`, car ce repli réinstallerait une dépendance à la fois, exactement ce que ce module supprime. Trois processus node disparaissent aussi par étape (npm → shell → outil), c'est-à-dire trois `node.exe` de moins sur la table de fork. Le pin écrit dans `node_modules/.bin` reste nécessaire aux **entrées** npm lancées avec un shell (`npm run lint`, `npm test`) et aux shells interactifs ; la chaîne, elle, n'en dépend plus. Le `timeout` du watchdog est désormais **par maillon** : un maillon bloqué est tué (arbre entier) et **nommé**, au lieu d'emporter les treize autres.

**Chaque run termine par la répartition de son temps** : coût par maillon, part du total, écart avec l'exécution précédente (le rapport lit le cache **avant** de l'écrire), et ce que paralléliser les maillons indépendants rapporterait — **chiffré, avec sa contrepartie** : `lint`, `l10n` et `audit-gate` ne font que lire, donc ils sont parallélisables, mais chaque processus concurrent de plus charge la table de fork msys, c'est-à-dire la pression qui fabrique la panique. Les maillons d'hygiène (sweeps chrome/electron, purge de sortie) sont mesurés eux aussi : ce sont des secondes réelles, et un maillon qu'on ne mesure pas est un maillon sur lequel personne ne peut décider.

**Et deux maillons portaient presque tout le temps, pour rien.** Le coût n'était pas dans les quatorze petits contrôles (100–850 ms chacun, mesurés) mais dans `tsc --noEmit` (**33,4 s**) et `eslint .` (**7,4 s**), rejoués en entier à chaque exécution — et deux fois par changement, puisque le saut « déjà vérifié » ne couvre par définition pas un arbre modifié. Trois drapeaux rendent cette répétition inutile : `--incremental --tsBuildInfoFile node_modules/tsconfig.tsbuildinfo` (tsc), `--cache --cache-location node_modules/.eslintcache` (eslint), `--cache --cache-location node_modules/.stylelintcache` (stylelint). Mesuré, mêmes maillons et mêmes seuils : `lint` passe de **46,6 s à 15,4 s** (tsc 33,4 → 7,8 s, eslint 7,4 → 2,0 s). Les caches vivent sous `node_modules/`, que git ignore : un cache **traqué** aurait sali l'arbre à chaque run, ce qui aurait **annulé** le saut « déjà vérifié » — les deux accélérations se seraient éteintes l'une l'autre. Et rien n'est devenu plus permissif : `--max-warnings 0` et `--noEmit` sont assertés **à côté** des nouveaux drapeaux (`tests/lint-chain-speed.test.ts`), parce que « plus rapide » ne doit jamais vieillir en « plus tolérant ». Aucun de ces caches n'est partagé avec la CI : un runner part froid, donc le job qualité continue de tout vérifier de zéro. Un cache n'est pas une confiance : une erreur de type et une violation `no-explicit-any` réintroduites **avec les caches chauds** sortent toujours en rouge (vérifié par sonde), parce que les deux sont indexés sur le **contenu** du fichier, pas sur sa date.

**Runbook unique : [`docs/FORK_PANIC.md`](docs/FORK_PANIC.md)** — symptômes exacts, **quel mécanisme couvre quoi** (et ce qu'il ne couvre pas), table de décision, récupération manuelle pas à pas, limites connues. `DEVELOPMENT_HISTORY.md` reste la trace datée des mesures ; le runbook décrit l'état actuel.

**Précondition vérifiée, pas supposée** : Windows compose le PATH en [machine puis utilisateur] et `cmd.exe` essaie les extensions dans l'ordre, donc un `git.cmd` ne peut être atteint que si son **dossier précède tout dossier contenant un `git.exe`**. L'installeur fait deux auto-tests et **échoue** (`exit 1`) quand le shim est parasité par un `git.exe` du PATH machine, en nommant le remède : `git --version` répond la même chose dans les deux cas, donc il ne prouve rien. Tant que le dossier du shim n'est pas en tête du PATH **machine** (droits admin), le shim est installé mais jamais exécuté — `npm run git:retry -- <commande>` reste alors le chemin fiable.

**Un hoquet de plateforme n'est pas un verdict — mais une écriture rejouée peut être un doublon.** Mesuré le 2026-09-12 : trois runs du pixel-check PDF passés au rouge le même jour sur un **504 du gateway Supabase**, application intacte — et une suppression de compte éphémère qui a pris le même 504, donc un résidu resté en base (le garde anti-résidus l'a signalé au run suivant : son travail, mais un run trop tard). `scripts/lib/transient-http.mjs` porte la seule décision qui manquait : **quand** réessayer. Un **verdict** (400/401/403/409/422) n'est jamais retenté — quatre tentatives sur un refus, c'est quatre fois le même refus ; une **coupure** (429/502/503/504, erreurs de transport) l'est, **bornée** et **journalisée** (`↻ … HTTP 504 — coupure passagère, tentative 2/4`), parce qu'une reprise silencieuse rendrait « vert » indistinguable de « ça a fini par passer ». À l'épuisement, on rend **ce qu'on a vu** — le dernier statut, ou l'erreur relancée : jamais un succès inventé, jamais une exception avalée.

**Un `HTTP 200` ne prouve pas que la prod sert le build qu'on teste.** Les E2E post-déploiement attendaient un 200 de la racine — et un 200 est satisfait par le déploiement **précédent** : pendant la propagation de l'alias Vercel, un cache de bord sert encore l'ancien HTML, et le pixel-check partait alors juger le build d'un **autre commit** que le sien. Un rouge pareil coûte plus qu'un rouge absent : il envoie chercher une régression de rendu là où il n'y a que quelques secondes de propagation. Le build écrit donc son identité dans son HTML (`scripts/lib/build-stamp.mjs`, `<meta name="build-sha" content="…">` — le sha vient de `BUILD_SHA`, posé explicitement par le job de déploiement), et l'attente exige **cette** identité (`scripts/wait-for-deployment.mjs`) : tant que la prod sert le build d'avant, elle réessaie, et son refus nomme la **PUBLICATION**, jamais le rendu — `stale` (une autre identité), `not-live` (404 `DEPLOYMENT_NOT_FOUND`), `serving-error` (5xx, un hoquet de plateforme) et `unreachable` sont réessayés puis accusés différemment. Et une page **sans** identité n'est pas un vert de plus : `unknown` est refusé, parce qu'**invérifiable n'est pas un vert** — un E2E qui juge un build qu'il ne peut pas nommer vaudrait le 200 qu'on vient de retirer. Le même raisonnement s'applique à la navigation du pixel-check : un délai de navigation ou un 5xx servi par la plateforme est **repris** (`↻ navigation : … tentative 2/3`) et, s'il persiste, nommé comme un problème de plateforme ou de réseau **du runner** — jamais comme une régression de l'application. Enfin une connexion ratée n'est plus avalée : l'ancienne version imprimait `✅ connecté` alors que le formulaire était resté affiché, et le run mourait plus loin sur un « bouton introuvable » — un rouge qui accusait l'application d'un problème de transport. Toutes les reprises du run sont **dites avant le verdict** (`↻ 2 reprise(s) de transport pendant ce run`), parce qu'un vert du troisième essai ne raconte pas la même chose qu'un vert du premier.

**Et une lecture faite juste après un envoi de formulaire ne parie jamais sur le délai.** Audit du 2026-09-13 : la chaîne E2E lisait la base **une seule fois**, 2–3 s après l'envoi, à **sept** endroits — la classe, l'élève, le solde, le parent, l'employé, le salaire, la dépense fournisseur. Deux situations très différentes se lisaient donc identiquement : *« l'écriture n'est pas encore visible »* et *« l'écriture n'est jamais partie »* — et le run rouge accusait l'application d'un simple retard. Le salaire avait déjà sa boucle (son commentaire dit pourquoi : « mesuré, le même run passait 3 fois et échouait la 4ᵉ »), la dépense fournisseur a reçu la sienne après avoir rougi de la même façon ; les cinq autres passent maintenant par **la même brique** (`scripts/lib/read-after-submit.mjs`). Trois propriétés portent : le **premier essai ne paie aucune attente** (quand la base est à jour, le cas courant, le contrôle ne coûte rien) ; on n'attend pas *une ligne* mais **l'état attendu** (un solde qui doit passer à 50 000, un statut qui doit devenir `unpaid` — une ligne rendue avec l'ancienne valeur n'est pas un succès) ; et le **nombre de lectures est publié** (`absence après 7 lecture(s)`, `↻ la base a rattrapé en 3 lecture(s)`) pour qu'un run qui a attendu ne se lise pas comme un run instantané. La cadence est **injectable** (`read` et `sleep`), donc chaque propriété se prouve sans réseau ni vraie horloge. Enfin deux lectures oubliaient de demander l'`id` de la ligne qu'elles venaient de créer (le parent, la dépense fournisseur) : l'identifiant restait `null`, donc le contrôle de résidu **par identifiant** était silencieusement écarté — un contrôle qui ne peut pas nommer ce qu'il cherche ne peut pas le retrouver.

**Et une écriture ne se rejoue jamais à l'aveugle** : un 504 tombe souvent *après* que la requête a été appliquée, et `public.staff` n'a **aucune** contrainte d'unicité (`public.students` n'a d'unique que `student_id`, NULL sur les lignes de démo) — le doublon serait alors invisible, parce que le nettoyage supprime par l'id rendu par la tentative gagnante. D'où `replayableWrite(write, probe)` : **avant chaque reprise**, une sonde demande si l'écriture est déjà passée et, si oui, c'est **son** résultat qui est rendu ; une sonde qui échoue ne décide rien (on rejoue) ; le premier essai ne sonde jamais, sinon chaque écriture paierait un aller-retour pour rien. Le compte éphémère porte un email unique, donc rejouer à l'aveugle aurait rendu un 422 — et le run serait mort **avant** d'avoir l'uid, c'est-à-dire sans rien à supprimer. Enfin le garde anti-résidus porte `if: always()` dans `pdf-e2e.yml` — c'est quand la chaîne casse au milieu qu'un compte reste en base — et compte un `404` à la suppression comme **déjà absent** (une reprise qui a abouti), pas comme une purge ratée.

## PR Dependabot — jamais de vérifications périmées

GitHub n'a **aucune** option « rebaser automatiquement quand la base change » : le seul rebasage automatique de Dependabot concerne les **conflits**, pas l'obsolescence. Une PR Dependabot dont les checks ont tourné sur un état de `main` qui n'existe plus reste donc verte-sur-du-vide — et la commande `@dependabot rebase` postée par un workflow avec le `GITHUB_TOKEN` est **refusée** depuis 2023 (« only users with push access can use that command »).

`.github/workflows/dependabot-rebase.yml` comble ce trou : à chaque push sur `main` (et une fois par jour, pour les PR ouvertes *après* le dernier push), il liste les PR `dependabot/*` de ce dépôt visant `main`, demande leur avancement, met la branche à jour, et se rabat sur `@dependabot rebase` en cas de conflit — Dependabot sachant régénérer le lockfile, pas nous. Les PR de fork ne sont **jamais** touchées.

**Le token est un PAT, jamais le `GITHUB_TOKEN`** — c'est le point que ce fichier existe pour rendre impossible : une mise à jour faite avec le `GITHUB_TOKEN` ne déclenche **aucun** workflow (son push est invisible pour Actions), donc la branche serait à jour et les vérifications toujours périmées, en vert. Un PAT produit un push d'utilisateur, `synchronize` part, et la chaîne qualité rejoue réellement. Pour l'activer : créer un PAT (fine-grained : *Contents* + *Pull requests* en lecture/écriture ; classic : scope `repo`) et le poser dans **Settings → Secrets and variables → Actions** sous le nom `DEPENDABOT_REBASE_TOKEN` — pas dans « Dependabot secrets », qui ne sert qu'aux workflows déclenchés **par** Dependabot. Sans ce secret le job avertit et sort en 0 ; le mettre à jour est volontairement un geste humain. `tests/dependabot-rebase.test.ts` verrouille l'invariant : le workflow ne référence aucun `GITHUB_TOKEN`, et le script ne le lit jamais.

**Poser (ou remplacer) ce secret sans `gh`** — il n'y a aucun CLI GitHub sur les postes de ce dépôt, et l'API n'accepte qu'une valeur **chiffrée** (sealed box libsodium) : lire `GET /repos/:owner/:repo/actions/secrets/public-key` (`key`, `key_id`), calculer `crypto_box_seal(secret, base64_decode(key))`, puis `PUT /repos/:owner/:repo/actions/secrets/DEPENDABOT_REBASE_TOKEN` avec `{ encrypted_value, key_id }`, sous un token qui a les droits d'**admin** du dépôt. Et la règle qui évite le pire : **un PAT révoqué sans remplacement laisse le workflow vert et inerte** — c'est le secret qu'il faut remplacer, pas seulement le PAT qu'il faut révoquer. Un secret mis à jour est immédiatement pris en compte, aucun commit nécessaire.

**Mesuré le 2026-09-12, après avoir posé le secret** : `workflow_dispatch` → le job a rebasé les **3 PR ouvertes** (#43, #44, #46), et leurs **6 vérifications** chacune ont rejoué sur les nouveaux sha (`08:19:28`–`08:19:32`, toutes vertes, dont le contraste de thèmes — qui ne demande plus aucun secret). C'est exactement ce qu'un push au `GITHUB_TOKEN` n'aurait pas produit : la branche à jour, les vérifications périmées. L'audit a suivi tout seul, sans être touché : `Dependabot rebase … preuve structurée : a agi`, et `npm run check:automations` sort en **0**.

### Un run vert ne prouve rien — `npm run check:automations`

C'est ce même secret manquant qui a rendu nécessaire le workflow `automation-audit.yml` : `Dependabot rebase` était **vert à chaque push depuis 22 runs sans jamais rien rebaser**, et rien dans la liste des runs ne distinguait ça d'un run qui avait mis trois PR à jour. La règle est écrite une fois (`scripts/lib/automation-evidence.mjs`) : **une automatisation qui ne peut pas agir le DIT**, et une qui agit le dit aussi — les deux par une **preuve publiée**, jamais déduite d'un run vert. L'audit lit, pour **chaque** workflow, le dernier run **terminé** sur `main`, puis les **étapes** de ses jobs et leurs **annotations stockées** : une preuve qui nomme ce workflow et déclare ne pas avoir agi est un **échec** (vert sans avoir agi) ; une preuve **absente** alors que le run portait l'étape de preuve est un échec aussi (`unproven` : un run qui ne prouve rien est le faux vert que cet audit pourchasse) ; une preuve **illisible** est un échec (invérifiable n'est pas un vert) ; un cron sans run récent est un échec (un cron qui ne part pas est en panne) ; et un audit qui n'a **rien** pu lire en est un (un token sans `actions: read` ressemble à un dépôt propre). Un run **antérieur** au contrat est `legacy` — nommé, non bloquant — et le contrat s'applique de lui-même au run suivant : c'est plus honnête qu'une fenêtre de tolérance devinée, qui laisserait un faux vert passer pour une course de plateforme. Un run **rouge** est signalé sans doubler l'alerte, et un run **en cours** n'est jamais pris pour une dormance. Le job demande `actions: read` **et** `checks: read`, tourne au push et une fois par jour, et **ne bloque aucun déploiement** : c'est un signal, pas une porte.

**La preuve ne voyage plus dans un journal — elle est STOCKÉE.** Le transport a été remplacé le jour où ses trois défauts ont été nommés : le runner réécrit ce qui traverse un journal (le titre d'une annotation disparaît, un contrat posé là a été vert, testé, et aveugle sur le run qu'il visait), n'importe quoi qui **imprime** une marque se fait passer pour l'automatisation qui l'émet, et GitHub n'archive un journal qu'**après** avoir marqué le run terminé (d'où des `logs 404` sur des runs verts qui venaient de finir, et toute une mécanique de fenêtre de grâce). Chaque automatisation publie donc sa preuve par une étape **nommée** (`Publier la preuve d’action`), que le runner stocke en **champs structurés** (titre + message d'annotation) ; `npm run check:automations` lit ces champs par l'API (`checks: read`) et ne télécharge **aucun** journal.

**Et la substance doit venir de l'automatisation, pas de son lanceur.** Le canal était juste et la mesure manquait : l'étape publiait une **phrase écrite dans le YAML**, la même qu'un script ait tout mesuré ou rien regardé — un vert conditionnel à « les étapes d'avant n'ont pas rougi ». Depuis, chaque automatisation qui a du code à elle publie **ses propres chiffres**, depuis le script qui les a mesurés (`scripts/lib/evidence-publisher.mjs`) : le gate d'audit dit ses deux comptes npm, la veille Vercel son verdict (épinglé, arbre de la dernière release), le contrôle RLS le nombre de sondes **réellement exécutées** contre la base, le nettoyage E2E les enregistrements parcourus, l'audit des automatisations les workflows jugés, le rebase Dependabot les PR examinées. Deux garde-fous rendent la chose vérifiable : le script ne publie que s'il en a le **mandat** (`AUTOMATION_EVIDENCE: '1'`, posé par l'étape qui l'exécute — une suite de tests qui lancerait le même script reste muette : c'est le défaut du 2026-09-12 fermé à la racine, et non plus seulement constaté), et son sujet est **son identité** (son fichier de workflow) ou, pour un script partagé par deux workflows (l'audit RLS anon), celui que le runner impose. Le CLI (`scripts/publish-automation-evidence.mjs`) reste pour les automatisations **sans** script à elles — déploiement Vercel, empaquetage Windows : là, la seule chose mesurable est que la commande tierce est allée au bout, et le compte de l'installeur est lu **sur le disque** (`ls release/*.exe`) — un build qui n'a rien sorti publie une **inaction** et rougit. Enfin la **marque textuelle a disparu** (`AUTOMATION-EVIDENCE ` n'existe plus) : le titre sélectionne, le message **est** le payload. Il n'y a donc plus un caractère à imiter pour se faire passer pour une preuve — il faut un vrai payload, avec un vrai sujet. Le refus, lui, reste le même partout : raison vide, `--acted` avec `--count 0`, ou les deux états à la fois, et **une preuve refusée fait rougir le producteur** (une automatisation qui ne peut pas prouver ce qu'elle a fait n'est pas verte). Un run qui avait l'étape de preuve et n'a rien publié est un **faux vert** (`unproven`) ; un run **antérieur** au contrat est `legacy` — nommé, non bloquant, jugé sur sa seule conclusion — parce que l'audit lit les **étapes** du run pour savoir si une preuve était attendue, au lieu de deviner une fenêtre de tolérance.

**La chaîne E2E retente sans doubler PARTOUT, et parle désormais pour elle-même.** Le pixel-check PDF était le seul à porter les deux moitiés — la reprise des coupures avec rejeu sondé, et une preuve **mesurée**. Les autres scripts de la chaîne avaient l'une ou l'autre, jamais les deux. La garde CSP et `e2e-business.mjs` séparent maintenant `rawApi` (la brique des **écritures**) de `api` (celle des **lectures et mutations**, retentée et journalisée) : la séparation **est** le contrat, parce que retenter une écriture depuis la couche de transport doublerait la ligne que la sonde de `replayableWrite` sert justement à ne pas créer. `verify-desktop-app.mjs` retente ses deux suppressions et **nomme** l'état obtenu — un 404 compté comme « déjà absent » (c'est ce que le nettoyage demande), et une panne de nettoyage **dite** là où un `catch(() => {})` laissait une ligne en base sans laisser de trace.

**Le dernier maillon sans la double brique était le garde-fou RLS — celui qui juge les droits des autres.** `verify-anon-rls.mjs` savait déjà **sonder avant de rejouer** ses écritures, mais son transport ne retentait rien : un **504 du gateway** sur une lecture était lu `!res.ok`… donc comme un **refus anon**, et la passe sortait **VERTE** sans avoir rien prouvé — le miroir exact du faux rouge du pixel-check (là, un hoquet passait pour une brèche ; ici, il passait pour une preuve). Le transport vient désormais de `transient-http.mjs` : les coupures (429/5xx, pannes réseau) sont reprises, bornées et journalisées, et ce qui **survit** à la reprise devient une sentinelle `{status: 0}` — **inconclusif** (skip, exit 0), jamais un refus ni une brèche. La cadence est **injectable** (`retry` : essais, attente, `sleep`) pour que les tests ne la paient pas — la suite reste sous la seconde. Cinq cas la verrouillent : un 504 passager sur une lecture est rejoué (**2 appels** mesurés sur cette table), un 504 qui persiste rend la passe **inconclusive** au lieu de verte, un verdict **401 n'est jamais rejoué** (1 appel mesuré malgré 3 essais autorisés), un 504 sur l'**écriture** de sonde ne double pas la ligne (la sonde retrouve la ligne déjà appliquée — **1 seul POST**), et le balayage anti-résidus des comptes `ci-probe-*` passe par `fetchRetried` : c'est précisément ce 504-là qui avait laissé un compte en base le 2026-09-12.

**Et les deux autres automatisations qui parlent au réseau remplaçaient la brique par une boucle maison, qui rejouait les verdicts.** `check-vercel-pins.mjs` rejouait un **401** (token expiré) et un **404** quatre fois de suite ; `rebase-dependabot-prs.mjs` rejouait trois fois tout ce qui n'était pas 401/403/422. Dans les deux cas, un refus n'était pas réparé par la reprise : il était seulement **retardé**. Les deux passent maintenant par `withTransientRetry`, et la mise à jour de branche est un **rejeu sondé** : le `PUT update-branch` porte un `expected_head_sha`, donc un rejeu non sondé après un 504 rend un **422** que la boucle de décision lit comme un **conflit** et « répare » en postant `@dependabot rebase` sur une PR déjà à jour. La sonde relit la tête de la PR : si elle a bougé, l'écriture est déjà passée, et c'est son résultat qui compte. Un test verrouille les deux moitiés (brique partagée + sonde) et **interdit le retour de la boucle maison**.

**Et chaque maillon publie SA mesure, pas une phrase de workflow.** Trois producteurs pour `pdf-e2e.yml` : la garde CSP ses pages principales parcourues en session réelle et ses violations détectées (`7/7` pages, `0` violation), **chaque invocation** du pixel-check ses vérifications passées sur le document produit (`--mode auto` et `--mode recu-parent` publient chacune la leur, l'audit les additionne), et le garde anti-résidus ses enregistrements parcourus en base. L'étape « Publier la preuve d'action » **reste**, pour ce qu'aucun script ne peut mesurer : que la chaîne **entière** soit allée au bout — l'étape d'en-têtes, écrite en YAML sans script à elle, et l'**ordre** des gardes. Deux scripts E2E supplémentaires (`e2e-business.mjs`, `verify-desktop-app.mjs`) publiaient leur compte mesuré mais **se taisaient** : aucun workflow ne les exécutait, et c'est le **mandat** de l'étape qui fait parler un producteur, jamais le script — un contrôle que rien ne lance est un contrôle qui n'existe pas. Ils tournent désormais (voir « Preuves qui tournent vraiment » ci-dessous), sous le mandat de l'étape qui les exécute. Un test le verrouille — chaque producteur de la chaîne publie un **compte**, pas seulement « j'ai agi » — parce qu'une preuve sans rien à compter vaut pour un script qui a tout mesuré comme pour un script qui n'a rien regardé.

**Un contrôle qui lit des preuves doit se méfier de sa propre suite de tests.** C'est exactement ce qui a coûté le 2026-09-12 : l'audit cherchait un mot dans des journaux, or `npm test` exécute des suites *qui parlent de ces mots-là*. Le 2026-09-12 il a donc accusé `Quality & performance guard` avec le motif de `Dependabot rebase` : la marque avait été **imprimée** dans le journal du job de tests par le script Dependabot lui-même (`main()` tournait à l'import), et l'audit lisait ce journal. Trois protections le rendent impossible : la preuve **porte son sujet** (le payload nomme le workflow ; elle n'est comptée que s'il est celui du run jugé, et l'emprunt est **cité** quand il ne correspond pas) ; **importer un module ne travaille pas** (`npm run check:import-effects` refuse tout module importé par une suite qui écrit dehors à l'import) ; et **la commande d'annotation ne s'imprime que par les deux modules du canal** (`npm run check:gate-sentinels` : 165 fichiers scannés, liste blanche réduite au CLI et au producteur partagé, commentaires blanchis — un commentaire ne s'exécute pas).

**Et l’immunité de chaque contrôle est désormais inventoriée** (`npm run check:guard-immunity`), parce que trois pièges réparés sur place — un par contrôle — ne tiennent que tant que personne n’ajoute un contrôle. Chaque `scripts/check-*.mjs` doit se **déclarer** dans `scripts/lib/guard-immunity.mjs` avec **ce qu’il lit** (source, journaux, configuration, processus, réseau) et les immunités qu’il porte : **non-vacuous** (il refuse de conclure sur zéro fichier — sortie **2**, pas 1 : ce n’est pas une violation, c’est une vérification impossible), **prose-blind** (il lit par `scripts/lib/source-text.mjs`), **stored-fields** (il lit des **champs stockés** — les annotations d’un run — jamais le texte d’un journal), **subject-identified** (une preuve **nomme** son émetteur). La preuve doit être **visible dans la source**, ou l’exemption doit **dire pourquoi** : une exemption muette est un échec, une entrée périmée aussi — un inventaire qui garde des garanties sur du code disparu vaut moins que rien. Les huit scans de source partagent maintenant **une seule** couche de blanchiment, et c’est en la factorisant qu’un défaut a été **mesuré** : le scanner de TypeScript seul se désynchronise après une interpolation (le `}` doit être **rescanné** en fin de gabarit, ce que fait le parseur et que ne fait pas un scan jeton par jeton). Deux conséquences vues dans ce dépôt : un commentaire de 70 lignes avalé dans un jeton de gabarit — le contrôle des emojis accusait alors de la **prose** — et du texte de fixture exposé comme du **code** — le contrôle d’intégrité accusait le mauvais fichier. Les plages de littéraux viennent donc du parseur, les commentaires du scanner, et un `//` qui tombe dans un littéral n’est pas un commentaire.

**Et une écriture de démo doit pouvoir être RETROUVÉE** (`npm run check:e2e-writes`) : une ligne qu’on ne sait pas retrouver est une ligne qu’on ne sait pas supprimer. C’est ce qu’a montré le 504 du 2026-09-12, tombé **après** avoir appliqué un POST. Le rejeu — le travail de `withTransientRetry` — a créé son risque propre : un **doublon**. Bénin là où une contrainte d’unicité l’interdit, sauf qu’il n’y en a aucune : le schéma est formel, `public.staff` n’a rien d’unique sur `email`, `public.students` n’a d’unique que `student_id` (NULL sur les lignes de démo). Le nettoyage supprime par l’**id rendu par la tentative gagnante**, donc la ligne de la tentative perdue n’aurait jamais eu de nom — et la garde anti-résidus ne surveille que les comptes éphémères. Le contrôle exige donc, pour **chaque création** des `scripts/` qui touchent la base partagée : un **enrobage rejouable** (sonder avant de rejouer), un **jeton d’exécution** (ce qui rattache la ligne à SON run), et une **clé de réconciliation** (une **requête** qui la retrouve — `=eq.…` en REST, `?email=` en GoTrue — jamais l’id rendu).

**Trois indirections, résolues plutôt que tolérées** — parce qu’un faux rouge apprend à éteindre un contrôle, et qu’un contrôle éteint ne protège plus rien. Le **jeton** est cherché **par symbole** : `const TS = Date.now()…`, `ephemeralEmail(…)`, `randomUUID()`, et les constantes bâties sur elles (`const PROBE_NAME = \`RLS ${TS}\``) — c’est la **citation** qui compte, jamais la déclaration. La **clé** d’une **aide** se vérifie chez **tous ses appelants** : `insertOnce(table, row, find)` vit dans `verify-pdf-download.mjs` et tient sa clé de ses quatre appels, et un seul oublié rendrait l’aide incapable de retrouver sa ligne — c’est **l’appelant fautif** qui est nommé, pas la définition. L’**enrobage** se lit sur les appels qui **encadrent** le site (comptage de parenthèses jusqu’à la fin de l’instruction), jamais dans un voisinage. Et le contrôle lit la version **blanchie des commentaires** (`scripts/lib/source-text.mjs`) : la phrase qui explique `email=eq.…` ne fait pas passer un POST qui ne l’écrit nulle part.

**Les exemptions sont bornées dans les deux sens.** Une seule existe : les trois **sondes de refus** de `verify-anon-rls.mjs` — des POST que la RLS *doit* refuser, qui n’ont donc rien à réconcilier et ne laissent aucune ligne. Le compte est **écrit** dans l’exemption et vérifié de part et d’autre : un site de plus (« migrez, ou élargissez en le justifiant ») **et** un site de moins (« une exemption qui ne correspond plus au réel doit être abaissée, sinon elle autorise un retour en arrière silencieux ») font échouer le contrôle ; une exemption muette, ou nommant un script disparu, aussi. **Quatre écritures réelles ont été migrées avec lui** : le compte jetable de `e2e-business.mjs`, celui de `verify-csp-guard.mjs`, le compte **et** la ligne d’employé de `verify-desktop-app.mjs` (sondés par email et par nom — le nom porte déjà le jeton du run), et les quatre de `verify-anon-rls.mjs`, dont le nom de sonde porte désormais le sien (`CI Probe — anon RLS ${TS}` : un nom fixe faisait ressembler deux exécutions à la même ligne). Mesure sur l’arbre : **6 scripts, 11 créations toutes traçables, 41 mutations**.

**Ce que la suite de ce contrôle a attrapé, et qui vaut d’être dit** : trois faux verts, tous trouvés par les cas écrits pour lui. Un `const TS = Date.now()` dans l’en-tête du fichier **estampillait** à lui seul toutes les écritures situées en dessous (un `Date.now()` nu n’est plus un jeton). `${supabaseBase}` comptait comme un jeton alors qu’il construit une **URL** (une interpolation ne vaut que si le symbole interpolé en est un). Et la fin d’une instruction se lisait en **colonne 0**, donc jamais pour du code indenté : une aide définie soixante lignes plus haut passait pour l’enrobage du site. Trois façons d’être vert sans rien vérifier — et la seule raison pour laquelle elles sont fermées est que `tests/e2e-writes.test.ts` joue ces cas sur les **vrais scripts** du dépôt, pas seulement sur des cas inventés.

**Conséquence assumée** : tant que `DEPENDABOT_REBASE_TOKEN` n'est pas posé, ce job est **rouge** — il nomme l'automatisation morte qui était verte depuis 22 runs. En local : `GITHUB_TOKEN=… npm run check:automations` (les runs ne sont pas publics, et il faut `actions: read` **et** `checks: read` pour lire les étapes et les annotations ; sans token le script sort en **2** au lieu de rendre un vert qu'il n'a pas mesuré).

## Une seule base de données pour tout le monde

Tous les postes — l'installeur Windows, le site déployé — doivent lire et écrire la **même** base Supabase : un paiement saisi au bureau doit apparaître sur le portable du directeur. Ça n'était vérifié nulle part : la ref `rpcjdohfxwukbqngbprw` était écrite dans 16 endroits dispersés (`vercel.json`, quatre workflows, six scripts, l'historique) et **jamais dans l'application**, tandis que `.env` n'est pas commité (donc c'est ce que la machine de build avait sous la main) et que `.env.staging` nomme un autre projet. Deux installations pouvaient donc viser deux bases, chacune croyant voir les données des autres.

**La base partagée est nommée une fois** : `scripts/lib/shared-project.mjs` (importé par l'application *et* par les contrôles, donc pas deux définitions qui s'accordent aujourd'hui et divergent demain). Elle déclare aussi la **seule** dérive autorisée — staging, avec un jeu de données de test, à condition de déclarer `VITE_APP_ENV=staging` pour ne jamais se présenter comme la production.

**`npm run check:shared-db`** lit deux choses, parce que ce ne sont pas les mêmes vérités : les **fichiers d'environnement** (ce que le prochain build lira — là où une dérive se prépare) et l'**artefact construit** avec `--dist` (ce qui est réellement embarqué dans le JavaScript livré — là où une dérive se prouve). Un `.env` juste et un paquet faux (mode oublié, variable injectée par la plateforme, cache) ne se distinguent que par la lecture du paquet. Le garde-fou tourne dans la chaîne qualité **et** dans `electron:dist` / `electron:release` **avant** l'empaquetage. Un artefact sans aucune URL Supabase est un échec, pas un vert : une application qui ne joint aucune base ne sert personne.

**Le site DÉPLOYÉ est vérifié à part**, parce qu'aucun fichier ne peut le faire : `npm run check:shared-db:live` lit la page réellement servie, suit les modules qu'elle charge — la page n'en nomme qu'un, les autres sont dans le code, dont celui qui porte le client Supabase — et exige la base partagée. C'est la seule lecture qui attrape une variable d'environnement changée dans le tableau de bord de l'hébergeur, qui n'existe nulle part dans ce dépôt. Le workflow `shared-db-watch.yml` l'exécute à chaque push **et une fois par jour** (une bascule de réglage ne produit aucun commit). Mesure du 2026-09-12 : `mama-thera-finance.vercel.app` sert bien `rpcjdohfxwukbqngbprw`, la même base que l'installeur.

**Et l'origine que l'application EMBARQUE est relue à chaque déploiement.** Un `vercel deploy` qui rend 0 ne dit qu'une chose : la commande a abouti. Le 13/09, un domaine du projet répondait `HTTP 404 DEPLOYMENT_NOT_FOUND` pendant que le job de déploiement était vert — et l'application de bureau, elle, **embarque** une origine (`electron/main.cjs` bascule dessus quand son interface locale ne démarre pas) : un poste dont le chargement local échoue n'avait donc plus rien à charger, et personne ne l'aurait su avant qu'un utilisateur ne le dise. Le job de déploiement relit désormais l'origine **après** avoir déployé, et exige trois choses distinctes, parce qu'elles se réparent différemment : qu'elle **réponde** (DNS, TLS, statut — un domaine mort est le cas mesuré), qu'elle serve **l'application** (une page de plateforme servie en 200 est le faux vert le plus trompeur, il a le bon code), et que **ses modules se téléchargent** (une coquille dont le bundle répond 404 est un écran blanc, c'est-à-dire le même défaut un cran plus loin). L'origine est écrite **une seule fois** (`electron/public-origin.cjs`), lue par le poste et par le contrôle : la porter en clair des deux côtés, c'est deux écritures qui s'accordent le jour où on les écrit. **Et ce n'est pas la seule URL embarquée que le contrôle relit.** Le dépôt a payé une fois le prix d'une adresse que personne ne relisait, donc les autres sont inventoriées au même endroit (`electron/embedded-links.cjs`) : l'origine de repli, la **page de téléchargement** où atterrit un poste portable (il ne s'auto-installe pas — c'est sa seule porte de sortie pour reprendre une version), et le domaine des **liens de notification** d'un parent. Chacune est jugée par **sa catégorie**, parce que « ce lien marche » ne veut pas dire la même chose pour une application qu'on sert, pour une page qu'on ne sert pas et pour un domaine qui n'est pas le nôtre : l'origine doit répondre, servir la **coquille** et ses **modules** ; la page de téléchargement doit répondre **et atterrir sur une page de version** (mesuré : `302 → /releases/tag/v1.0.8` — un 200 qui mène ailleurs n'y permet rien) ; le domaine tiers doit **répondre**, et un 4xx y est un **avertissement** nommé, pas un refus — juger le code d'un serveur qu'on ne sert pas produirait un rouge permanent sur un lien sain, et un contrôle toujours allumé ne se lit plus. En clair : `🔎 liens embarqués par l'application`, puis une ligne par lien (`fallback-ui`, `releases-page`, `whatsapp`), chacune disant ce qui a été lu — et un lien qui n'atterrit pas où il doit nomme **l'endroit à réparer**. Ajouter un lien à l'inventaire sans lui donner de règle est un **refus** : un lien qu'on ne sait pas juger n'est pas un lien vérifié. Et le contrôle tourne là où l'application est **livrée**, jamais dans la chaîne locale — un commit ne doit pas dépendre du réseau pour être vérifié. **Il ne tourne pas seulement au déploiement** : une origine se casse aussi — et surtout — **sans commit** (domaine remappé, projet dont le déploiement de production est supprimé dans le tableau de bord, réglage d'hébergeur basculé, certificat expiré). Aucun de ces gestes ne réveille un contrôle déclenché par un push, donc une **veille quotidienne** (`public-origin-watch.yml`, 06:35 UTC) relit la même origine par le même script, et **son contrôle publie lui-même ce qu'il a mesuré** — statut, taille de la coquille, nombre de modules réellement téléchargés — au lieu de laisser une étape YAML affirmer « j'ai agi ». Mesure du 2026-09-13, sans jeton : l'origine embarquée rend `HTTP 200 · 1 module · application/javascript`, l'ancienne origine morte rend `HTTP 404 — « The deployment could not be found on Vercel. »` avec le remède nommé, et un domaine qui ne résout pas sort en nommant `ENOTFOUND`.

**Et l'installation le dit elle-même** : une base illisible ou divergente affiche un badge rouge « Base non partagée » — y compris en production, contrairement aux badges d'environnement. L'état dangereux est celui où chacun voit ses propres données en croyant voir celles des autres ; il ne doit jamais être silencieux.

## Les comptes propriétaires — un compte qui disparaît ne se découvre plus à la connexion

Le 13/09, `ibrahimkalilthera@mamathera.org` — le **compte dev**, documenté dans ce dépôt depuis le premier jour — **n'existait plus** en base. Personne ne l'avait supprimé volontairement : un script jetable lisait `users[0]` d'une réponse d'API en croyant lire son propre compte (le filtre `?email=` de GoTrue est **ignoré**, mesuré — réparé depuis, `scripts/lib/ephemeral-accounts.mjs`). Toute la chaîne qualité était verte pendant ce temps, et c'est normal : **ce qui manquait n'était dans aucun fichier**. Le défaut n'a été vu qu'au moment où son propriétaire a voulu se connecter — c'est-à-dire trop tard, et par la seule personne qui ne pouvait rien y faire.

**`npm run check:owners`** lit donc l'état de la **base**, seul endroit où la réponse existe, et il publie trois preuves distinctes parce qu'elles se réparent différemment : **(1) présence** — chaque compte du roster (`scripts/lib/owner-accounts.mjs`, une seule liste) est là, et son absence est l'incident, donc rouge ; **(2) état** — confirmé, non suspendu, non supprimé en douceur, joignable par mot de passe, et rôle de `user_profiles` conforme à la documentation (un compte présent mais inutilisable serait un faux vert) ; **(3) login RÉEL** — un compte de contrôle est créé, on s'y connecte pour de vrai par le chemin exact de l'application (clé anon), puis il est supprimé — la seule mesure qui attrape « la base répond mais l'authentification ne délivre plus de session ». Pour les comptes du roster eux-mêmes, le login réel est mesuré dès que le mot de passe est fourni par l'environnement (`OWNER_*_PASSWORD`) : **aucun mot de passe n'est écrit dans le dépôt**, et sans la variable le login est annoncé **NON MESURÉ** — une absence nommée, jamais comptée comme un vert. Sans secrets du tout, le contrôle est **indécis (exit 2)** : un contrôle qui ne peut pas regarder ne félicite personne.

**`owner-accounts-watch.yml`** l'exécute à chaque push **et une fois par jour** (une suppression ne produit aucun commit), sans bloquer aucun déploiement. Mesure du 2026-09-13 après la restauration : `✅ 4 compte(s) propriétaire(s) présents et conformes, 1 hors service, 2 login(s) réel(s) aboutis`.

## Session — 45 minutes d'INACTIVITÉ ferment la session, et un rechargement ne la ferme pas

La fenêtre est de **45 minutes sans aucun geste de l'utilisateur**, la même pour **tous les comptes** (une constante dans `src/app/useInactivityLogout.ts`, pas un réglage par équipe — la ligne `inactivity_minutes` de `app_settings` a été retirée par migration). Un préavis de 60 secondes s'affiche avant la coupure, avec « Je suis toujours là » : sans lui, une saisie longue serait coupée au milieu sans que rien n'ait prévenu.

Ce qui compte comme un geste : appui (souris, doigt, stylet), touche au clavier, défilement, molette, et déplacement de la souris (au plus une fois toutes les 30 s, pour ne pas recalculer un minuteur à chaque pixel). Rester devant une page sans rien toucher **est** de l'inactivité, par définition.

**Un rechargement (F5) n'est PAS un départ, et c'est délibéré.** Une première version révoquait la session au déchargement (`pagehide`/`beforeunload`) pour couvrir la fermeture ; mesuré, elle fermait aussi la session sur un simple F5 — inacceptable. Aucune API de navigateur ne distingue un F5 d'une fermeture au moment du déchargement, donc la seule façon d'épargner F5 est de **ne rien révoquer à cet instant** ; c'est cette règle-là qu'un test verrouille (aucun fichier de `src/` n'enregistre d'écouteur `pagehide`/`beforeunload`).

Fermer l'onglet ou l'application **ferme quand même la session** : la session vit dans `sessionStorage` (`src/lib/supabaseClientCore.ts`), donc elle meurt avec l'onglet — un effet du stockage, pas d'un geste au déchargement. `tests/inactivity.test.tsx` (10 cas) mesure la fenêtre exacte, le préavis, les cinq familles de gestes, la souris, l'innocuité sans session, l'absence de révocation au déchargement, et **que la classe est fermée** (plus aucun fichier de `src/` ne lit `inactivity_minutes`).

## Sauvegarde de la base — une erreur de manipulation ne doit plus être définitive

Jusqu'au 13/09/2026, ce dépôt n'avait **aucun** moyen de sauvegarder la base : pas de `pg_dump`, pas de script, aucune procédure. La seule copie des données d'école vivait dans un projet Supabase, et une suppression par erreur — celle du compte dev l'a montré — n'avait aucun retour possible.

**`npm run backup:db`** lit les tables déclarées **une seule fois** (`scripts/lib/db-tables.mjs`, dans l'ordre où elles peuvent être réécrites : `students.parent_id` référence `parents`, `payments.student_id` référence `students` — restaurer dans le désordre écrit des lignes que la base refuse), et écrit deux fichiers : le contenu, et un **manifeste** qui dit ce qu'il contient (lignes et empreinte **par table**, empreinte du fichier, projet, date). « Sauvegarde OK » sans chiffres ne se distingue pas d'un export vide, et un export vide est un cas légitime : la différence doit se lire.

**`npm run backup:verify`** relit cette sauvegarde **sans aucune base de données** — ni credentials, ni réseau. Il déchiffre, vérifie le manifeste et recompte chaque table : une sauvegarde qu'on n'a jamais rouverte n'est pas une sauvegarde. Et **`npm run restore:db`** la réécrit de façon **idempotente par construction** (`on_conflict` sur la clé primaire + `resolution=merge-duplicates`, sonde qui relit la ligne par sa clé avant tout rejeu), après **trois refus** : un contenu qui ne correspond pas à son manifeste, une cible non vide (sauf `--force`), une sauvegarde venue d'un autre projet (sauf `--allow-project-mismatch`).

**Le chiffrement est obligatoire en CI.** Le workflow `backup-watch.yml` (quotidien, 02:20 UTC) refuse de tourner sans `BACKUP_PASSPHRASE` et refuse d'écrire en clair : un artefact de workflow est téléchargeable par n'importe qui dans un dépôt **public**, donc un dump lisible qui remonte ici serait exactement la fuite que les autres veilles existent pour empêcher. L'archive chiffrée (AES-256-GCM, scrypt) est conservée 30 jours, et le script publie sa mesure. Le jour où l'on restaure vraiment, la phrase est le seul secret à retrouver : **sans elle, la sauvegarde est un fichier mort** — c'est le prix du chiffrement, et il est écrit dans `docs/BACKUP.md` plutôt que découvert ce jour-là.

**Et une sauvegarde qu'on n'a jamais remise est une hypothèse.** `backup-roundtrip.yml` prend donc une sauvegarde **réelle** de la base partagée, démarre une **pile Supabase locale vide** (Docker, les 22 migrations), y **remet** cette sauvegarde, puis `npm run backup:roundtrip` **recompte la cible lui-même** et exige l'égalité avec le manifeste : il ne croit ni le script de sauvegarde ni celui de restauration. Une table qui perdrait des lignes rend le job rouge **en la nommant** ; les lignes dont le compte `auth.users` n'existe pas dans la cible sont calculées et comptées à part (leurs mots de passe ne voyagent pas par l'API REST) ; et si la base est vide de données d'école, le verdict le dit.

**Une mise à jour ne touche pas les données.** Celles de l'école vivent dans la base **partagée**, jamais dans l'application : mettre à jour remplace des fichiers de programme sur le poste. Ce qui vit **sur** le poste — la **file d'attente hors ligne** (un paiement saisi sans réseau, de la vraie donnée qui n'existe nulle part ailleurs) — est rangé dans `userData`, nommé par `appId`/`productName` qui n'ont pas changé depuis la première version, et `deleteAppDataOnUninstall: false` fait que même une désinstallation ne l'efface pas. `tests/update-retention.test.ts` verrouille ces trois faits, parce qu'un renommage les emporterait **sans qu'aucune erreur ne se lève**.

**L'année scolaire de travail vient du CALENDRIER, et elle avance toute seule.** Le 2026-09-13, un élève enregistré a « disparu » : deux valeurs par défaut vivaient chacune de son côté — l'app s'ouvrait sur `2026-2027` **écrit dans le code** et filtrait listes et tableau de bord dessus, pendant que le formulaire naissait en `2024-2025` (l'autre littéral) et **écrivait** ça. L'élève était dans la base et invisible, ce qui se lit « mes données ont disparu ». Le premier remède a fait venir l'année de `academic_years.is_current` — nécessaire, et **insuffisant** : c'est un réglage manuel, et il était déjà **périmé** dans la base (il disait 2025-2026 pendant que l'app affichait 2026-2027). Une année qui dépend d'un geste annuel revient toujours avec un an de retard. La règle est donc le calendrier : une année scolaire va du **1er septembre au 31 août** (`schoolYearName`), l'année de travail est celle du jour, et le choix d'un poste (`mama_thera_selected_year`, stocké **avec sa date**) n'est respecté que s'il appartient à l'année scolaire en cours — un poste resté sur l'an dernier repart donc de lui-même sur la rentrée. Trois exceptions, chacune mesurée : une déclaration `is_current` **en avance** sur le calendrier est suivie (une école peut préparer la rentrée), une déclaration **en retard** est ignorée (c'était la panne), et l'année du calendrier est retenue **même quand la base ne la connaît pas encore** — un 1er septembre, personne ne l'a créée. C'est `keepAcademicYearCurrent` qui la crée et déplace le drapeau : le premier administrateur qui ouvre l'app ce jour-là fait la rentrée pour tout le parc, sans y penser. `src/lib/academicYears.ts` porte la règle (pure, **21 cas** dans `tests/academic-years.test.ts`, dont le passage 2026-2027 → 2027-2028) ; le provider n'invente plus aucune année, et le formulaire **écrit celle qu'il affiche**.

**`npm run repair:academic-year -- --from <année> --to <année> [--current] [--yes]`** reclasse des lignes déjà rangées sous la mauvaise année (ce que le littéral a laissé). Elle **compte** d'abord, table par table, ce qu'elle déplacerait — la liste des tables qui portent une année est **demandée à la base**, pas supposée — n'écrit que sur `--yes`, puis **recompte les deux années** : une mutation qui répond 200 sans rien déplacer serait un faux vert. Elle refuse un `--from`/`--to` manquant, une cible absente d'`academic_years` et deux années identiques (`scripts/lib/year-refile.mjs`) ; `--current` déplace le drapeau `is_current` sur la cible, sans quoi les lignes reclassées resteraient invisibles à l'ouverture. Mesure du 2026-09-13 : `3 ligne(s) reclassée(s) de « 2024-2025 » vers « 2026-2027 » — recompté : 0 / 3`, vérifié ensuite par un vrai login et les lectures de l'application.

## Mise à jour automatique des postes installés

Une version publiée doit atteindre **tous** ceux qui ont installé le setup, sans qu'ils aient à y penser. L'auto-update utilise le flux GitHub Releases (`electron-builder` publie `latest.yml` à côté de l'installeur) et **vérifie à trois moments** : au démarrage, **toutes les 30 min** (une application d'école reste ouverte toute la journée — c'est ce qui manquait), et **au retour sur la fenêtre**, avec 10 min d'espacement minimal.

**Le canal est ouvert depuis la v1.0.1** — et c'est ce que la preuve locale ne pouvait pas dire : le mécanisme était vert alors qu'**aucun release n'existait**, donc chaque poste interrogeait un flux vide. Vérifié comme l'application le lit, sans authentification : `releases.atom` → `releases/download/v1.0.1/latest.yml` (identique au fichier construit, octet pour octet) → installeur, dont le **sha512 recalculé est celui inscrit dans `latest.yml`**.

⚠️ Le release est ouvert par `scripts/publish-release.mjs`, **pas** par `electron-builder` : le build tourne en `--publish never` et ne fait que produire des octets. C'est ce qui rend le piège des deux brouillons impossible — `electron-builder --publish always` ouvrait **un release par cible** (NSIS puis portable), donc deux brouillons pour un même tag, les artefacts **répartis entre eux** (l'un `latest.yml` + les exe, l'autre le blockmap), et promouvoir le mauvais publiait un release **sans `latest.yml`**, c'est-à-dire une mise à jour que personne ne voit. Un brouillon reste invisible pour `electron-updater` (`No published versions on GitHub`) : **publier le release fait partie de la mise à jour**, sinon la version n'existe pour personne.

**« Plus tard » reporte, il ne refuse pas** : la question revient 15 min après, et la version est déjà téléchargée. Une fois prête, l'interface l'annonce en permanence (bandeau « redémarrer ») — une boîte de dialogue fermée ne revient pas, un bandeau reste. Le processus principal pousse son état au renderer ; le pont `preload` expose seulement lire / s'abonner / installer / relancer.

**Au-delà du seuil, la mise à jour n'est plus une question.** Atteindre tout le monde ne suffit pas : « Plus tard » accordé indéfiniment laisse un poste des mois sur la même version **sans que personne n'ait jamais décidé de ne pas la faire**. Trois seuils (`electron/updater-policy.cjs`, pur donc testé comme une décision) rendent l'installation **obligatoire** : une version **majeure** de retard, **deux mineures** dans la même majeure, ou une version **publiée depuis 45 jours** et toujours pas installée — ce dernier attrape le cas le plus courant, la « petite » version sortie un jour où personne n'était devant le poste. Là, le retard est **décidé par le processus principal** et poussé à l'interface, qui le montre **sans pouvoir le fermer** : écran plein, pas de croix, pas de « plus tard » dans la boîte de dialogue (ni d'échappement par Échap), relance **toutes les minutes** au lieu d'un quart d'heure.

**Frein d'urgence : une version retenue n'est ni proposée, ni imposée, ni installée.** Une porte qui force est indispensable — et dangereuse le jour où la version publiée est défectueuse. Deux leviers, et ils ne couvrent pas la même chose :

- **Retirer le release** (supprimer le release et son tag) : le geste qui vaut pour **tous** les postes, y compris ceux dont la version installée ne lit pas le frein — `electron-updater` ne voit plus cette version dans le flux. C'est le premier geste.
- **Publier une retenue** dans [`updates/holds.json`](updates/holds.json) (`{"version": "1.0.4", "reason": "…"}`), un fichier **hors du release** donc modifiable **après** publication : le poste cesse de proposer *et* cesse d'imposer, sans attendre que le release soit retiré. Lu à chaque vérification, depuis `app-update.yml` (le propriétaire et le dépôt ne sont pas recopiés ailleurs).

Trois propriétés, chacune testée : une retenue **bat le forçage** ; une liste **illisible ne force RIEN** mais continue de **proposer** (on ne contraint pas un utilisateur sur une supposition — même asymétrie que pour une version illisible) ; et le frein tient sur **tous** les chemins qui mènent à l'installation — l'annonce, le rappel déjà programmé, le bouton, et l'« installation à la fermeture » d'`electron-updater`. ⚠️ Conséquence assumée de la deuxième : un poste qui **ne peut pas lire** la liste (réseau du site) n'impose plus rien — le prix du « on ne force pas sur une supposition », et il se voit au journal (`retenues illisibles …`). ⚠️ Et un frein n'agit que sur les postes dont la version installée **contient ce frein** : livré en **1.0.3**, il ne protège pas les parc plus anciens, pour lesquels seul le retrait du release fonctionne.

**La preuve est faite sur le binaire livré, pas seulement en unité** : `node scripts/verify-updater.mjs` sert un flux local à l'exe empaqueté, et joue **une passe par règle** — parce qu'un seul scénario ne peut en prouver qu'une, et que la règle qui attrape les postes d'école est celle de la **date** :

```
patch   même majeure, correctif récent      → NE DOIT PAS être obligatoire
age     même majeure, publié il y a > 45 j  → OBLIGATOIRE (… toujours pas installée)
minor   deux mineures de retard             → OBLIGATOIRE (2 version(s) mineure(s) de retard)
major   une majeure de retard               → OBLIGATOIRE (1 version(s) majeure(s) de retard)
hold    LA MÊME que « age », mais retenue   → AUCUNE obligation + installation refusée
blocked LA MÊME que « major », téléchargement en échec (404 servi)
                                            → `poste bloqué (download)` au
                                              journal, ET une entrée écrite dans
                                              `update-journal.jsonl` sur le poste
```

L'exigence ne porte pas seulement sur « obligatoire oui/non » mais sur le **motif annoncé** : sans lui, une règle qui forcerait tout le temps passerait pour verte dans les trois passes obligatoires. Les seuils (45 jours, 2 mineures, 1 majeure) sont **lus dans `electron/updater-policy.cjs`**, jamais recopiés — une preuve qui recopie un seuil finit par prouver une règle que le code a quittée. Chaque passe exige en plus un **téléchargement réel** (`download-progress`, cache invalidé entre les passes) et **au moins deux vérifications dans la même session** : mesuré, `check focus` ouvre le bal, `check startup` est refusé comme trop rapproché, puis l'intervalle redéclenche. `UPDATER_PASSES=age,major` restreint le run.

La passe **`tampered`** de `scripts/verify-updater.mjs` prouve ce chemin sur le binaire empaqueté : le flux sert les **vrais** octets sous une **autre** empreinte (et la **même taille**, pour que le verdict tombe sur « ce ne sont pas les octets promis » et non sur « téléchargement tronqué »), et la passe exige le refus **écrit**, le cache **purgé**, une entrée `checksum` **en file** — et que la cause soit `checksum`, **pas `download`**.

**Une seule issue de secours, et seulement là où l'obligation serait un blocage** : quand le téléchargement a **échoué**, « continuer sans mettre à jour » redevient possible et un bouton relance la vérification. Un poste qu'on ne peut pas mettre à jour ne doit pas devenir un poste inutilisable — et cette issue **disparaît** dès que la version est téléchargée, donc elle ne peut pas servir d'échappatoire quand tout va bien. Deux asymétries assumées, dans le sens de l'horloge qui recule : une version **illisible** ne force **rien** (forcer est une contrainte sur l'utilisateur, on ne l'impose pas sur une supposition), et une date de publication absente n'annule que la règle de date — chaque règle juge ce qu'elle sait.

**La version portable** ne peut pas s'auto-installer (`electron-updater` exige l'installeur NSIS) : elle vérifie quand même et reçoit un **lien vers la page des versions** — ne rien pouvoir faire n'excuse pas de ne rien dire.

**Et une porte fermée ne doit pas être un silence.** Un poste bloqué le disait à personne : ses échecs partaient dans `console.log` du processus principal — donc nulle part pour qui n'ouvre pas les outils de développement, et **personne** ne les ouvre sur un poste empaqueté. Un poste d'école pouvait donc rester des semaines derrière la porte sans que l'administrateur sache ni qu'il l'était ni pourquoi. `electron/updater-policy.cjs` décide désormais **quand** un poste est bloqué (`gateFailure`, pur donc testé), et quatre causes seulement — parce que les confondre noierait le vrai cas sous le bruit de la progression normale :

- **`install`** — une installation a été tentée et le poste est **revenu sur la même version**. Le plus silencieux des quatre : l'utilisateur a cliqué « Redémarrer maintenant », il a redémarré, rien n'a changé. Signalé **même hors obligation** — une installation qui n'aboutit pas est un fait, pas une opinion sur le retard ;
- **`manual`** — la porte est fermée et ce poste ne peut **structurellement** pas la satisfaire (version portable : `electron-updater` exige l'installeur NSIS). Il ne faut pas le forcer, il faut une main humaine ;
- **`download`** — obligatoire, et le téléchargement a échoué : le poste attend devant une porte fermée qu'il ne peut pas ouvrir seul ;
- **`checksum`** — les octets reçus **ne répondent pas** à ce que `latest.yml` annonce. Signalé **même hors obligation**, comme une installation non aboutie, et pour la même raison : c'est un fait, pas une opinion sur le retard.

**Pourquoi `download` et `checksum` ne sont pas la même ligne — et pourquoi ça a demandé un module.** Une mise à jour ne s'installe pas sur une version : elle s'installe sur une **promesse d'octets**. Un échec de réseau (proxy, coupure, réseau d'école) se répare **sur le poste** — on réessaie ; une promesse non tenue se répare **sur le canal**, et **tous les postes sont concernés**. Les confondre sous un seul mot envoie l'administrateur chercher une panne d'école qui n'existe pas pendant que le release servi reste faux. `electron/update-feed.cjs` relit donc la promesse dans le flux **du poste** (`latest.yml`, l'URL venant d'`app-update.yml` — jamais recopiée), **rehache les octets** restés sur le disque, et rend un verdict nommé. Trois précisions qui font le verdict : des octets **tronqués** restent un échec de téléchargement (on ne juge pas la promesse sur des octets incomplets) ; si la bibliothèque a **déjà écarté le fichier**, son propre refus reste la preuve — c'est elle qui a comparé les octets à la promesse ; et quand rien ne peut être conclu, le poste **n'accuse pas** le canal (une accusation sans preuve enverrait corriger un release innocent). Sur un verdict `checksum`, le poste **refuse** ces octets (ni installation immédiate, ni installation à la fermeture, ni depuis un rappel déjà programmé), **purge le cache** qui les resservirait sans réseau à la vérification suivante, et **inscrit la panne** — elle remonte au prochain démarrage connecté comme les autres. Le rapport d'audit, lui, ne dit plus « mise à jour obligatoire » d'une promesse non tenue : il dit **« mise à jour refusée — les octets servis ne répondent pas au flux »**, parce qu'un intitulé qui nomme la mauvaise porte fait chercher au mauvais endroit.

Ce qui s'annonce, c'est un **fait daté** : l'état bloqué, le retard, le poste, la version visée — et ce qui va être fait (savoir si le poste a été mis à jour ou non).

**Deux canaux, parce que l'un des deux peut manquer.** Le **journal local** (`update-journal.jsonl`, dans `userData`) ne dépend d'aucune session ni d'aucun réseau : il est donc la première moitié, et **le seul canal qui existe sur un poste bloqué avant toute connexion**. Il est **borné** (200 entrées, les plus récentes), **jamais fatal** (disque plein ⇒ `false`, la mise à jour continue) et **lisible à la main** — une ligne = un objet JSON, et une ligne coupée par une coupure de courant est ignorée à la lecture au lieu de rendre le fichier illisible. L'**envoi au journal d'audit** est la seconde : il exige une session, et c'est ce qui fait que l'administrateur n'a pas à visiter chaque machine. Le rapport **nomme le poste** (première question : « lequel ? »), la version visée et le **motif recopié** de la politique — jamais un résumé. Il part **tout seul**, sans qu'on clique (attendre un clic, c'est rester muet tant que personne n'est devant l'écran), **une fois par blocage** (la vérification revient toutes les 30 min, et remplir le journal d'audit de la même panne le rendrait illisible), et un envoi impossible **le dit** : l'écran affiche le chemin du journal local plutôt qu'un « signalé » qui ne repose sur rien. Un bouton, **« Ouvrir le journal du poste »**, est là pour la personne devant la machine (le fichier est créé s'il n'existe pas — un cul-de-sac ne serait pas un remède).

**Et le journal local est une file d'attente, parce que le cas normal est un poste qui démarre bloqué DEVANT PERSONNE.** Le signalement ci-dessus part quand le poste est bloqué **et** qu'une session existe ; or un poste d'école fait exactement l'inverse — il bute à la première vérification de mise à jour, avant que quiconque se soit connecté, et c'est à cet instant que l'envoi au journal d'audit est **structurellement impossible**. Une entrée qui ne saurait pas attendre serait donc perdue, c'est-à-dire exactement le silence que ce mécanisme existe pour réparer. Le journal porte donc, depuis, une marque (`reportedAt`, nulle tant que rien n'est parti) et deux canaux bornés la vident : `updates:pending-reports` lit la file, `updates:mark-reported` marque **ce qui est réellement parti**. C'est AppShell qui la vide — seul endroit qui connaît la session — **au premier démarrage connecté, une fois par utilisateur**. Trois décisions portent cette file, et chacune évite un défaut précis : la panne a une **identité** (code + version visée + version installée), donc les dizaines d'occurrences du même fait — la vérification revient toutes les 30 min — ne font **qu'une** remontée, tandis que `occurrences` conserve ce que la déduplication ne doit pas perdre (« bloqué 30 fois » qui se lirait « bloqué une fois » ferait passer une école pour un incident isolé) ; on ne marque **que ce qui est parti** (un envoi raté reste en file — marquer d'avance effacerait la panne d'un poste à cause de la panne du réseau, le mauvais sens de l'erreur) ; et un marquage impossible rend `{ marked: 0, written: false }` sans jeter, donc la panne repart au démarrage suivant — **un doublon vaut mieux qu'un silence**. Le rapport remonté se distingue du signalement en direct et porte **quand** le poste a buté et **combien de fois** ; une version visée **plus récente** est une information neuve, donc elle repart même si la précédente était déjà marquée.

**Et vingt postes bloqués par le même 404 ne doivent pas faire vingt lignes.** Le journal d'audit est écrit par POSTE — et c'est exact : une preuve ne se réécrit pas — mais ça ne répond pas à la question que l'administrateur se pose devant une école entière : **qu'est-ce qui est cassé, et combien de machines ça touche ?** Vingt lignes identiques à la station près noient le motif dans sa répétition, et un signalement qu'on ne lit plus ne signale rien. D'où un **regroupement par panne**, côté lecture et seulement côté lecture : `src/lib/blockedIncidents.ts` (pur, donc testé) transforme les remontées en **incidents**, et l'onglet Journal d'audit affiche **une ligne par cause** — combien de postes, lesquels, quand pour la première et la dernière fois, et combien de butées au total — avec un dépliage qui redonne **les remontées brutes, machine par machine**. Rien n'est réécrit ni masqué : le regroupement est un mode de lecture (désactivable), et l'export CSV suit la vue, sinon le tableur redonnerait exactement les vingt lignes qu'on vient de regrouper.

**Ce qui définit « la même panne », et ce qui refuse d'être fondu.** La clé d'un incident est celle que la politique et la file du poste ont déjà choisie — **code** et **version visée** — **plus le motif**, parce que le motif est ce qui sépare deux causes réelles : deux machines bloquées par le même code et la même version avec deux messages différents ne sont **pas** le même incident, et les fondre ferait disparaître une panne derrière l'autre. La **version installée** n'en fait pas partie : une même panne frappe naturellement un parc dont les postes ne sont pas tous au même numéro (1.0.3 → 2.0.0 et 1.0.4 → 2.0.0 bloqués par le même 404, c'est une panne, pas deux). Et une entrée **illisible** (ancien format, ligne retouchée) reste une ligne à part : on ne devine pas une panne à partir d'un texte qu'on n'a pas su lire, et la fondre la ferait disparaître — se tromper en séparant coûte une ligne de plus à lire, se tromper en fondant coûte une panne.

Preuve : `node scripts/verify-updater.mjs` (à rejouer après `npm run electron:dist`) sert un flux local, lance l'exe empaqueté et exige la chaîne `checking → available → progress → downloaded` **plus au moins deux vérifications dans la même session**, sur **les six passes** — chacune avec le **motif** que la règle doit avoir produit, et la passe `blocked` **lit le journal écrit par l'application** (pas son log de preuve) : c'est ce fichier-là qui existe chez un client. Le rythme est réglable pour la preuve : `UPDATER_CHECK_INTERVAL_MS`, `UPDATER_FOCUS_COOLDOWN_MS`, plus `UPDATER_FEED_URL` et `UPDATER_LOG_FILE` (mode preuve, sans boîte de dialogue), et `UPDATER_PASSES` pour ne jouer qu'une partie des passes.

## Version bureau (Windows)

L'application est aussi empaquetée en **application de bureau Windows** (shell Electron) :

- `electron/main.cjs` charge le **build local** de l'app (`electron-ui-dist/`) — le bureau s'ouvre même si le serveur Vercel est indisponible ; seuls les appels Supabase (login, données, PDF) passent par internet. Fallback : si le build local manque, l'URL hébergée est chargée.
- Sécurité : `contextIsolation` activé, `nodeIntegration` désactivé, sandbox activé ; les liens externes s'ouvrent dans le navigateur système ; les PDF téléchargés passent par une boîte de dialogue d'enregistrement (ou un dossier auto si `ELECTRON_DL_DIR` est défini).
- **Un téléchargement, une sortie** — et c'est vrai de tous les documents, pas du reçu. Deux endroits suffisent à faire arriver un PDF deux fois, et le 2026-09-13 les deux étaient là : côté Electron, laisser la routine d'enregistrement d'Electron décider **et** ouvrir son propre dialogue écrivait deux fichiers (`electron/download-policy.cjs` : soit un chemin imposé, soit les options du dialogue qu'Electron ouvre lui-même, jamais les deux) ; côté application, le mécanisme était **recopié** — quatre modules PDF, une cinquième copie à la main dans l'export CSV du journal d'audit, et un sixième chemin par `doc.save()` dans le relevé des parents. `src/lib/browserDownload.ts` est désormais le seul fichier du dépôt qui pose un attribut `download`, et un contrôle refuse un second émetteur comme le retour de `doc.save()`. Un seul endroit à changer le jour où la façon de télécharger change.
- Icône : emblème officiel « COMPLEXE SCOLAIRE MAMA THERA » (photo fournie, `build/icon.png` 512×512, coins transparents pour l'emblème circulaire — régénérable via `node scripts/generate-app-icon.mjs [image] [size]`).

**Build + installeur :**

```bash
npm run electron:ui      # vite build --base=./ --outDir electron-ui-dist
npm run electron:dist    # empaquetage Windows (NSIS + portable) + contrôle de cohérence du flux
# → release/MamaTheraFinance-<version>-setup.exe (installeur)
# → release/MamaTheraFinance-<version>-portable.exe (portable, sans installation)
```

**Vérification E2E du bureau** (login + navigation + téléchargement PDF dans l'app empaquetée) :

```bash
npm run electron:dist    # une fois, pour produire release/
node scripts/verify-desktop-app.mjs
# → prouve le binaire de la VERSION DU PAQUET (release/MamaTheraFinance-<version>-portable.exe),
#   déduite de package.json ; DESKTOP_EXE=… vise un autre binaire. Un artefact absent
#   est un ÉCHEC NOMMÉ — le dossier release/ accumule les versions, donc un défaut
#   écrit en dur (« -1.0.0- ») aurait pu prouver un binaire d'une autre version.
```

### Preuves qui tournent vraiment — deux workflows qui parlent pour elles

Un script E2E qui n'est exécuté par personne n'est pas un contrôle : c'est un fichier. `e2e-business.mjs` et `verify-desktop-app.mjs` publiaient déjà leur **mesure** — et aucun workflow ne les lançait. Ils ont maintenant chacun le leur, avec le déclencheur qui va avec ce qu'ils prouvent :

- **`business-e2e.yml`** — les deux **cycles métier complets** contre l'app **déployée** (élève → paiement → `amount_paid`, parent → salaire → dépense fournisseur), avec vérification de chaque ligne en base. Déclenché à la **fin d'un déploiement Vercel réussi** (comme le pixel-check PDF, avec le même gate : un deploy rouge ou annulé = skip neutre), plus `workflow_dispatch`. Le script vérifie la disparition des **lignes qu'il a créées** — par identifiant — plus cinq requêtes par préfixe de démo : « la base est vide » était vrai tant qu'elle ne contenait que de la démonstration, et devenait faux le jour où l'école saisit son premier élève. La garde anti-résidus passe en `if: always()`. ⚠️ Les deux workflow E2E qui écrivent en production (`pdf-e2e.yml`, `business-e2e.yml`) partagent le **même groupe de concurrence** : sans lui, chacun voit le compte éphémère **en cours** de l'autre et l'appelle un résidu — mesuré sur le premier run (18/19, tout vert sauf un résidu qui appartenait au voisin).
- **`desktop-e2e.yml`** — la preuve de l'application **empaquetée** : build de l'arbre (`electron:dist`, **sans** publication), puis lancement du portable en session vierge, connexion réelle, clic « Télécharger Reçu PDF », et vérification du PDF **sur le disque** (taille + signature `%PDF-`). Hebdomadaire + manuel, sur `windows-latest` : ce qui est prouvé n'est pas le site mais le **binaire**, donc le workflow le reconstruit au lieu d'attendre un déploiement. **Et il prouve une seconde fois, sur un autre objet** (voir ci-dessous).

**Ce que les postes reçoivent vraiment, exécuté et pas seulement lu.** Deux preuves différentes, et la différence est le sujet : la première construit (`electron:dist`) et prouve le portable de **ce commit** — c'est ce qu'un commit vaut ; la seconde ne construit rien, interroge le **canal** comme un poste (`/releases/latest`, **sans jeton** — un canal qu'on ne sait relire qu'authentifié n'est pas prouvé), vérifie les octets servis contre la **taille et le `sha512` du flux** en flux, **installe** l'installeur publié en silence (NSIS `/S /D=…`, désinstallé en fin de run), lance le binaire installé, se connecte, ouvre **Parents → « Ajouter Parent/Tuteur »**, et demande au **navigateur** ce qu'il impose (`node scripts/verify-installed-parent-form.mjs`). C'est ce qui manquait au correctif « l'adresse n'est plus obligatoire » : il avait été prouvé dans un `app.asar` **extrait** d'un installeur, c'est-à-dire **lu**, alors que le symptôme signalé est un **comportement** — un formulaire qui refuse l'enregistrement. Le verdict du contrat est pur (`scripts/lib/parent-form-contract.mjs`), donc chaque refus se prouve sans navigateur : un champ **introuvable** est un refus (un champ absent n'est pas un champ facultatif), et « le formulaire est valide sans l'adresse » ne compte que si le formulaire **redevient invalide** quand on vide un champ qui doit rester obligatoire (le nom) — sans cette lecture inverse, un gate mal lu rendrait le même verdict que la correction. Le contrôle **n'écrit** rien en base (il n'enregistre pas de parent) : il lit le gate du navigateur, ce qui prouve le blocage sans laisser de ligne à nettoyer.

**Les mettre dans un workflow a révélé quatre vrais défauts — et un cinquième sur le runner, ce qui est le meilleur argument pour le faire.**

1. **La preuve bureau détruisait sa propre mesure** : le script supprimait le dossier de téléchargement, *puis* lisait `statSync(pdf).size` pour composer sa preuve — un run parfaitement réussi finissait en `ENOENT` (PDF de 102 382 octets, deux lignes de démo pourtant supprimées). La taille est maintenant lue au seul moment où le fichier existe.
2. **Un binaire d'une autre version** : le chemin par défaut portait « `-1.0.0-` » en dur. Le dossier `release/` accumule les installeurs de toutes les versions, donc le jour où une 1.0.0 y traînait encore, la preuve aurait porté sur **un autre binaire** que celui du commit — et plus rien du tout dès qu'elle était nettoyée.
3. **Les cycles métier échouaient 5/7 sur l'app réelle**, pour trois raisons indépendantes, chacune invisible sans exécution : les **placeholders viennent des traductions** (`ex.` en français / `e.g.` en anglais) donc les chercher par leur texte exact liait le contrôle à une langue ; le champ « identifiant unique » d'un élève n'est **rendu que pour une classe de 9e année**, or le cycle crée une classe personnalisée — l'attendre faisait échouer le cycle sur un champ que cette route ne peut pas rendre ; et la page Dépenses porte **deux actions au libellé identique dans les deux langues** (« Ajouter une Dépense » / « Add Expense »), l'une écrivant dans `expenses`, l'autre dans `vendor_expenses`. Le cycle ouvre donc désormais le modal **par sa section** (l'en-tête de branche rendue porte le libellé de son onglet), pas par un libellé qui ne les distingue pas. Résultat mesuré : **19/19 vérifications**, aucune ligne de démo résiduelle après nettoyage.
4. **Le contrôle de résidu ne pouvait pas survivre aux données réelles** : il exigeait sept tables à zéro, ce qui devient faux dès le premier élève saisi par l'école — il vérifie maintenant les identifiants créés par le run (et un `-1` illisible reste un échec, ce qui a attrapé un `%` non encodé).
5. **Le binaire Electron manquait sur un runner propre** : `electron-builder` exige `node_modules/electron/dist`, que le postinstall d'electron télécharge, et un `npm ci` de runner ne l'a pas (mesuré : « The specified electronDist does not exist ») — défaut **latent dans le workflow de publication aussi**, qui n'a jamais tourné. `npm run electron:runtime` précède le build, une seule définition pour les deux workflows et pour la machine.

**Mises à jour automatiques** (`electron-updater`) : l'app installée (NSIS) vérifie les **GitHub Releases** de ce repo au démarrage et, si une nouvelle version existe, télécharge et installe l'installeur (dialogue « Redémarrer maintenant / Plus tard »). `latest.yml` est généré à côté de l'installeur — il doit être publié dans le même release. Publication :

```bash
npm run electron:release  # build (--publish never) + gate local + un release en BROUILLON
                          # contenant exactement les octets vérifiés (GH_TOKEN requis)
npm run release:promote   # promotion + relecture du flux SANS jeton (le geste qui livre)
# → le publieur téléverse lui-même, un fichier à la fois, dans UN SEUL release : l'état
#   trouvé (rien, un brouillon partiel, deux brouillons hérités) ne change pas la forme du
#   résultat. Le gate du brouillon est un SAS — un gate rouge laisse le release invisible,
#   donc rien n'est livré — et `--promote` enchaîne la preuve « comme un poste la lit »
#   dans le MÊME processus : une promotion sans relecture du canal n'est plus possible.
```

**Publier ne demande plus de clic : monter la version est le déclencheur.** `desktop-release.yml` ne se contente plus d'un `workflow_dispatch` — il part quand le run **qualité** de `main` finit vert, et un `gate` demande à `npm run check:release:needed` s'il y a un release à faire. La question est posée par la **même** décision que le gate d'avant-publication (`publishDecision`), donc les deux ne peuvent pas diverger, et la réponse est un **état** (`needed=true|false`), jamais un échec : un numéro déjà publié est le cas NORMAL d'un push qui ne monte pas la version, le job de publication est alors **sauté**, et l'audit le nomme « run sans objet » au lieu de le lire comme un run antérieur au contrat. Une fois le gate ouvert, ce qui suit est la chaîne d'avant, sans aucune intervention : `check:release:tag` → build signé → téléversement en brouillon → **consolidation des brouillons en double** → **promotion** → relecture du canal sans jeton. La seule main humaine qui reste sur cette chaîne est de **monter la version** : une décision, dans un commit relisible, pas un appel d'API.

Mesuré sur le canal réel, dans les deux sens :

```
v1.0.5 (déjà publié)  ➖ déjà publié (2026-09-12T22:32:24Z) — rien à publier : le parc a ce numéro   needed=false  exit 0
v1.0.6 (inédit)       ✅ inédit — il y a un release à faire                                          needed=true   exit 0
```

**Et l'automatisation a un prix, qui est un secret — mais il ne bloque plus la livraison.** Depuis le 2026-09-13, l'absence de certificat n'est plus un obstacle : la branche « aucun certificat » du job **construit et publie** un build sans `publisherName` promis, c'est-à-dire l'état que porte la **1.0.9** — la signature de **référence** de ce dépôt, désormais. Ce refus-là (publier sans certificat) avait eu une conséquence mesurée : il renvoyait la publication vers une machine locale, où le certificat de test attendait dans l'environnement — c'est le chemin qui a produit la 1.0.8 et gelé le parc. Ce que le certificat achète encore, et que rien d'autre n'achète, c'est le **nom de l'éditeur** : sans lui, Windows affiche « éditeur inconnu », et la preuve d'action du job l'écrit en toutes lettres (`installeur NON signé …`). Mesure du 2026-09-13 : les secrets du dépôt portent encore le certificat **de test** (`CSC_PFX_B64`, `CSC_KEY_PASSWORD`) — le garde-fou en refuse donc l'usage, et il faudra les remplacer par un certificat **approuvé** pour lever l'avertissement.

**Le publieur décide de la forme du release, et c'est ce qui rend le défaut impossible.** `scripts/lib/release-publish.mjs` porte le plan — pur, donc testé sans réseau — et il n'a que quatre issues : `create` (aucun release pour ce tag), `reuse` (un brouillon existe : on n'y téléverse que ce qui manque), `consolidate` (plusieurs brouillons : **une** cible conservée — celle qui porte déjà le plus d'artefacts attendus — les autres supprimés) et `refuse` (un numéro **déjà publié**, rien à publier, un artefact annoncé qui n'existe **nulle part**).

**Et la consolidation RÉUNIT avant de supprimer, sinon elle perd des octets.** Ce qu'un brouillon en double porte d'unique est rapatrié dans la cible — téléchargé en flux depuis l'API puis téléversé, jamais porté en mémoire — parce que supprimer un brouillon sans reprendre ce qu'il a d'unique fait disparaître un blockmap **sans que rien ne rougisse**, et chaque poste retélécharge alors l'installeur entier à chaque mise à jour. Ce qui compte est ce que le release doit porter, pas ce que ce dossier contient : `expectedArtifacts` élargit la liste de `latest.yml` — à l'étroit — avec ce que les brouillons du **même tag** portent déjà, donc l'ensemble publié ne dépend plus de l'état de `release/`. Deux pièges mesurés en chemin : l'API des actifs répond **302** vers `release-assets.githubusercontent.com` (un GET qui ne suit pas la redirection ne verrait **jamais** un octet, et paraîtrait simplement cassé), et une taille inconnue est un **échec nommé** — un `Content-Length` deviné est la seule façon de publier des octets tronqués en silence. À la fin, le release contient les octets vérifiés **et rien d'autre** : ce qui est en trop est retiré, y compris l'installeur d'une autre version qui traînerait là — c'est exactement le fichier qu'un humain télécharge à la main. La liste des octets publiés ne vient pas d'une liste écrite ici mais de `latest.yml` (`expectedArtifacts`, bâti sur `assetsToPublish`), donc de **ce que les postes lisent**, et un artefact annoncé introuvable **partout** (ni disque, ni brouillon) fait refuser la publication au lieu de publier un release incomplet.

**Le côté sûr est toujours de téléverser.** « Ne pas retéléverser ce qui est déjà là » est une optimisation, et une optimisation qui se trompe publie les mauvais octets : une taille égale **ne prouve pas** des octets égaux (un installeur reconstruit porte le même nom et une taille proche). Un téléversement n'est donc sauté que si l'API a renvoyé un `digest` qui correspond à l'empreinte calculée localement ; sans `digest`, « je ne sais pas » se traite comme « il faut téléverser ».

**La 1.0.6 est publiée, et le parcours a été refait à la main du début à la fin.** Aucun certificat de confiance n'existe (voir la section Signature ci-dessous) : la 1.0.6 a donc été construite **localement** avec un certificat **auto-signé de test** et publiée par ce publieur — un brouillon, 4 actifs, gate du brouillon vert, promotion, puis relecture **sans jeton** : la tête que le poste lit est `v1.0.6`, le `latest.yml` servi est **identique au construit octet pour octet**, l'installeur se télécharge (HTTP 206, `MZ`, 129 080 968 octets = annoncé), et les six versions publiées rejoignent la tête. La politique du poste en fait une **proposition** (`1.0.x → 1.0.y` est un écart de patch), qui devient **obligatoire au bout de 45 jours** si personne ne l'a prise. Deux défauts ont été trouvés en publiant pour de vrai : la promotion **taisait le verdict** de ses gates quand ils passaient du premier coup (le texte restait dans un tube — un succès silencieux n'apprend rien), et l'API de GitHub **remplace** la ressource, donc un `PATCH {draft:false}` sans `prerelease` transformait un brouillon pré-version en publication **stable** — tête du canal comprise. Les deux sont fermés, et le second l'a été par le contrôle du chemin des versions lui-même : il a refusé la promotion en nommant les six populations sorties du chemin.

**Prouvé en publiant pour de vrai, puis nettoyé.** Deux versions jetables (`0.0.1`, `0.0.2`) ont été publiées par ce programme de bout en bout : **un release chacune, 4 actifs, aucun brouillon** — puis releases **et** tags supprimés, pour qu'il ne reste rien dans le canal qu'un poste pourrait lire (`v0.0.x` n'aurait jamais été proposé à personne, mais un canal se lit aussi à la main). Et sur les vrais octets de production, le refus utile est vérifié : relancer le publieur sur la `1.0.5` **publiée** rend « `v1.0.5` est DÉJÀ publié — un même numéro ne peut pas changer de contenu : aucun poste ne verrait la différence. Montez la version. » `latest.yml` est toujours écrit par `electron-builder` malgré `--publish never` (vérifié sur un build réel : régénéré, 361 octets, identique à celui que les postes lisent). **Et la réunion est prouvée sur le canal réel, avec le piège reproduit à l'identique** : deux brouillons `v0.0.7` ont été fabriqués — l'un `latest.yml` + l'installeur, l'autre le blockmap **seul** — et le publieur les a consolidés en **un** release de 4 actifs, le blockmap **rapatrié depuis le brouillon supprimé** (téléchargé en flux, rehaché : identique à l'octet près), puis brouillon supprimé, release supprimé, **aucun tag créé** — le canal est revenu exactement à son état d'avant.

**Trois contrôles de cohérence, et chacun attrape une incohérence déjà payée.** Un poste se met à jour sur une **promesse d'octets** : `latest.yml` annonce une taille et un sha512, et `electron-updater` refuse tout ce qui n'y répond pas. Rien ne vérifiait cette promesse, et le dépôt l'a payé trois fois : une `1.0.1` publiée alors qu'**aucun release n'existait** (flux vide — tout le monde à jour de rien) ; un `electron-builder --publish always` créant **deux brouillons** pour le même tag, l'un portant `latest.yml`, l'autre le blockmap (invisibles pour l'updater) ; et un installeur reconstruit sous un numéro **déjà publié** (une republication n'atteint AUCUN poste, un même numéro ne se voit pas changer). D'où un contrôle à quatre modes, où l'empreinte est **recalculée sur les octets** — relire les trois mêmes fichiers ne prouverait rien :

```bash
npm run check:release          # 1. le paquet, latest.yml et les OCTETS du dossier disent la même chose
npm run check:release:tag      # 2. le numéro est inédit  ← le refus qui ne coûte encore rien
npm run check:release:draft    # 3. les octets TÉLÉVERSÉS répondent à latest.yml (brouillon)
npm run check:release:live     # 4. ce que les postes lisent répond à la promesse (rehaché depuis le dépôt)
npm run check:release:channel  # 5. le CANAL est encore vivant (release le plus récent + frein), SANS jeton
```

Le mode 1 est **inclus dans `electron:dist` et `electron:release`** (un build local refuse donc aussi un flux incohérent), le mode 2 tombe **avant** tout téléversement, et le mode 4 est le dernier pas du workflow — après la promotion, donc sur ce que les postes reçoivent réellement. Deux refus qui n'ont l'air de détails : deux releases pour un même tag (les artefacts sont **éparpillés** entre eux, et aucun outil ne les rassemble : c'est le brouillon en deux morceaux, mesuré), et un installeur d'une **autre version** présent dans le release (c'est le fichier qu'un humain téléchargera à la main). Et une panne de l'API est un **échec**, jamais un feu vert : un dépôt qu'on ne peut pas interroger ne prouve rien. Les installeurs d'anciennes versions qui traînent dans `release/` ne sont pas une erreur (le dossier accumule) mais sont **nommés** dans la sortie, parce que c'est exactement là qu'on prend le mauvais fichier.

**Et la promesse est vérifiée ENTRÉE PAR ENTRÉE, pas seulement sur sa première ligne.** `latest.yml` ne promet pas un installeur : sa liste `files[]` porte, ligne par ligne, une **taille** et un **sha512**, et c'est cette liste qu'`electron-updater` parcourt. Le contrôle ne comparait que le `path` du haut — donc une entrée ajoutée, servie par un autre objet, ou annoncée avec la taille d'un fichier qui n'est plus celui-là passait sans un mot : la première ligne répondait, la promesse de la seconde ne fut lue par personne. Désormais chaque entrée annoncée est **téléchargée et rehachée** — une seule fois par fichier, puisque le `path` figure aussi dans la liste et que hacher 129 Mo deux fois serait payer deux fois la même preuve — puis confrontée sur les **deux** grandeurs : la taille servie contre celle annoncée, le sha512 servi contre celui annoncé. Trois issues qui ne se confondent pas : une entrée **absente** du release est un refus nommé (« cette entrée-là du flux mène à un vide ») ; une entrée **présente mais illisible** est un refus dont le mot est la **LECTURE** (avec les deux voies et leurs statuts, parce qu'une lecture ratée n'est pas un fichier manquant — la confusion a déjà été payée ici) ; une entrée listée **sans** taille ni empreinte est un avertissement, pour que « listée » ne se lise jamais comme « prouvée ». Vérifié sur les octets **réels**, avec une seule et même lecture : tel que le flux l'annonce, vert (`129081184 octet(s) · sha512 b0BUIDaeiLnp… — taille et sha512 conformes à ce que le flux annonce`) ; la taille annoncée augmentée d'**un seul octet**, rouge (`taille 129081184 servie vs 129081185 annoncée`).

**Et le sens INVERSE est comparé lui aussi : ce qui est publié sans être dans le flux.** C'était la moitié invisible, et la plus dangereuse des deux — un installeur téléversé que `files[]` ne liste pas ne sera **jamais** téléchargé (`electron-updater` parcourt `files[]` et suit son `path`, rien d'autre) : le fichier est là, il pèse son poids, et aucun poste ne le verra, parce que rien ne manque là où on regarde. Chaque actif du release est donc **nommé**, y compris ceux qui ont le droit d'être hors du flux — « attendu hors flux » se lit, un silence ne se lit pas. Quatre issues, chacune avec sa raison : **`off-feed`** (normal et dit : `latest.yml` lui-même, le portable qui se télécharge à la main, le manifeste d'arborescence, et le **blockmap**, que le mécanisme différentiel découvre par convention à `<installeur>.blockmap` et non dans `files[]`) ; **`hole`** — un **installeur de la version annoncée** que le flux ne liste pas : c'est un **refus**, c'est un fichier publié pour personne ; **`foreign`** — un nom qui porte un **autre** numéro : nommé, pour que « le mauvais fichier repris à la main » ne reste pas possible sans être vu ; **`unknown`** — ni le flux, ni une catégorie connue : dit tel quel plutôt que rangé de force dans une case qui ne le décrit pas. La distinction blockmap/installeur n'est pas cosmétique : mesuré sur le canal publié (v1.0.8), le flux liste **un** fichier et le blockmap est un actif à part — en faire un défaut aurait allumé un avertissement permanent sur un canal sain, et un contrôle toujours allumé ne se lit plus. Sans flux lisible, rien n'est jugé : sinon chaque actif deviendrait « hors flux » et noierait la panne réelle (le flux manquant) sous une dizaine d'accusations qui n'en sont pas. Le rapport imprime les deux listes — ce que le flux annonce, **et** ce qu'il ignore :

```
   flux — 1 fichier(s) annoncé(s), chacun rehaché sur les octets servis :
   ✅ MamaTheraFinance-1.0.8-setup.exe · 129081184 octet(s) · sha512 b0BUIDaeiLnp… — taille et sha512 conformes
   hors flux — 4 actif(s) publié(s) que le flux ne liste pas :
   ➖ latest.yml — le flux lui-même — il ne se liste pas dans son propre `files[]`
   ➖ MamaTheraFinance-1.0.8-portable.exe — portable — hors du flux par conception : … se télécharge à la main
   ➖ MamaTheraFinance-1.0.8-setup.exe.blockmap — blockmap — hors du flux par convention : le différentiel le découvre à `<installeur>.blockmap`
   ➖ MamaTheraFinance-1.0.8-unpacked.manifest.json — manifeste d'arborescence — aucun poste ne le lit
```

**Et les nommer ne suffisait pas : ce qui est prouvé redondant part tout seul.** `npm run release:prune` décide du sort de `release/` par une règle et non par une date — un artefact ne disparaît que si le canal déclare un actif du **même nom, de la même taille et de la même empreinte** (le digest que GitHub calcule sur les octets qu'il sert), **sans télécharger un octet** : le plan se fait en métadonnées, les empreintes locales se recalculent sur le disque. Mesuré le 2026-09-13 : sept versions, 2,2 Go, **vingt et un fichiers** au même niveau — dont quatorze installeurs. Ce qui ne peut pas être prouvé **reste, et est nommé** : une version jamais publiée (sa copie locale peut être l'unique au monde), un actif que le canal ne déclare pas, une empreinte absente (une taille seule n'identifie pas des octets), et surtout une **empreinte qui diffère** — des octets locaux sous un numéro publié, c'est-à-dire le piège « un même numéro ne se voit pas changer », et c'est *aussi* l'alarme d'un canal qui servirait les mauvais octets, donc l'effacer effacerait l'alarme. D'où **deux actes distincts** : `--yes` enlève ce que l'empreinte autorise, `--yes --stale` enlève en plus les reconstructions locales d'un numéro **déjà publié** — leur justification n'est pas l'empreinte mais le fait que le numéro est pris, et elles ne partiront jamais sur un poste. Un brouillon ne peut rien autoriser : il est invisible pour un poste, donc il ne « détient » pas les octets là où un poste les lit. Par défaut il **n'enlève rien** : un plan qu'on ne relit pas est un plan qu'on n'a pas décidé. Les trois actes appliqués le 2026-09-13 : **2,2 Go → 754 Mo**, vingt et un fichiers → **six** entrées, dont **trois** seulement sont des artefacts livrables (le trio de la 1.0.6).

**Et un fichier qui porte le NOM d'un actif du canal sous d'AUTRES octets est un ROUGE — même quand c'est la version en cours.** C'est la variante dangereuse du piège, et elle a été mesurée avant d'être réglée : après l'acte `--yes --unpacked` sur l'atelier réel puis sa reconstruction, le build réécrit les installeurs, et l'atelier détenait un `MamaTheraFinance-1.0.6-setup.exe` qui n'était **pas** celui du canal — un poste qui l'aurait pris aurait reçu autre chose que ce que le canal publie — pendant que le contrôle répondait « atelier propre ». La cause tient en une ligne : la branche de la version en cours sortait **avant** toute comparaison d'empreinte (« elle ne peut pas partir, donc son empreinte ne décide rien »), vrai pour le rangement et faux pour la comparaison. Elle est comparée elle aussi, mais **seulement si le canal publie déjà ce numéro sous ce nom-là** : le flux ordinaire (monter en 1.0.7, construire, commiter) ne hache donc rien de plus et ne rougit pas, les mêmes octets que le canal restent une **conservation** — c'est la sortie du build que les preuves locales lisent — et un même nom aux octets différents est une **divergence**, donc une objection en `--check`. Le remède dépend du numéro et le rappel le dit : sur un **autre** numéro, `--yes --stale` la range (ces octets ne peuvent plus atteindre personne) ; sur le **numéro en cours**, aucun drapeau ne le fait — le rouge nomme les deux vraies voies, **restaurer les octets du canal** ou **prendre un numéro neuf**. Coût mesuré sur l'atelier réel, où la 1.0.6 est publiée : **2,0 s** pour hacher les 252 Mo de la version en cours, contre 0 avant.

**Et le fichier que les postes LISENT n'a aucun numéro dans son nom, donc il a sa propre lecture.** `latest.yml` est le seul fichier dont dépend **chaque** poste — `electron-updater` le lit à chaque vérification — et la règle qui compare les installeurs ne pouvait pas le voir : son nom ne porte pas de numéro, donc il tombait dans « hors sujet ». Un flux local qui déclare d'**autres** octets pour la **même** version — le fichier qui promet aux postes un contenu qu'il ne porte pas — passait donc inaperçu, alors que c'est précisément la divergence que la règle attrape pour les installeurs. Sa version vit dans son **contenu** : c'est le CLI qui l'y lit (`parseLatestYml`, l'unique propriétaire de « quelle forme a un fichier de flux »), et le module reste **pur** — il ne reçoit qu'un `declaredVersion` déjà lu. Trois lectures, trois sorts : mêmes octets que le canal ⇒ conservé, et la raison le dit ; autres octets ⇒ **divergence**, donc une objection en `--check`, et **aucun acte ne la range** (le publieur téléverse ce fichier à chaque release : un flux divergent se **restaure**, il ne part pas) ; version que le canal ne détient pas encore ⇒ rien à comparer, donc rien à accuser. Le coût est borné par la forme : un flux fait quelques centaines d'octets, et au-delà de 64 Ko ce n'est pas lui — donc rien n'est lu. Vérifié en mutant le flux **réel** de l'atelier : `--check` sort en **1** en nommant la taille (361 vs 387) et les deux empreintes, restauré aussitôt à l'octet du canal (`5d2dc022…`), et l'atelier redit « propre ».

**Et la dernière catégorie n'invoque aucune preuve, parce qu'il n'en existe aucune.** Une version que le canal n'a **jamais** eue n'a ni empreinte ni comparaison pour dire si sa copie locale est superflue — mais « jamais publiée » recouvre **deux situations opposées**, et les confondre serait dangereux. Un artefact ne part sur l'acte `--yes --unpublished` que s'il est **strictement plus bas que la version en préparation** (ce n'est donc pas le build qu'on s'apprête à livrer) **et strictement plus bas que tout ce que le canal détient** — le publier ferait donc *descendre* la tête, ce que le contrôle du canal refuse par construction puisqu'une tête qui descend coupe les postes installés au-dessus : ces octets-là ne peuvent plus atteindre personne. Un build **au moins aussi haut** que celui qu'on prépare est l'inverse exact — c'est peut-être celui qui attend sa publication, et sa copie locale en est l'**unique exemplaire** : **aucun drapeau ne l'enlève**, et le plan le dit dans ces mots. Une version illisible n'est jamais « plus basse » non plus : on ne devine pas un ordre à partir d'une chaîne libre. Et parce qu'aucune preuve ne peut décider, **qui décide est un humain** — le plan **nomme donc les candidats et la commande de l'acte même quand on ne l'a pas demandé** : garder en silence ne laisserait pas la décision à l'humain, il la lui cacherait. Et le rappel de fin **déduit ses drapeaux du plan** au lieu de les écrire d'avance : mesuré le même soir sur ce dossier, le plan de la 1.0.0 seule annonçait « Applique-le : npm run release:prune -- --yes » — or `--yes` seul n'applique que les départs qu'une empreinte autorise, donc l'exécuter n'aurait **rien** enlevé. Un plan qu'on croit appliqué et qui n'a rien fait ne se relit pas comme un plan vide : il se relit comme un ménage fait.

**Le rappel porte aussi son DOSSIER, et le nom du dossier n'existe qu'à un endroit.** Mesuré en montrant le plan d'un `release-probe/` : la ligne proposait d'agir sur `release/` — aidant, et faux, c'est-à-dire la seule façon dont un rappel peut être pire que rien, puisqu'il se recopie tel quel. `pruneCommand(plan)` déduit désormais les drapeaux **et** le dossier du plan, et il écrit le dossier **toujours** — défaut compris (`npm run release:prune -- --dir=release --yes`). Il a existé une forme courte (`-- --yes`) qui se taisait sur `release/` au motif que c'est la ligne de la documentation : elle faisait dépendre la correction d'une convention de lecture (« sans `--dir`, c'est le défaut »), et c'est exactement ce genre de convention qui a coûté deux fois ici — une ligne longue se lit, une ligne courte se devine. Le même défaut vivait dans le **contrôle de cohérence**, qui accepte pourtant `--dir=` : son avertissement sur les installeurs d'autres versions disait `release/` en dur, donc un contrôle lancé sur un autre dossier parlait d'un dossier qu'il n'avait pas lu — deux lignes du même rapport désignant deux endroits. L'avertissement nomme maintenant le dossier réellement parcouru. Et le nom du défaut est une **constante exportée** (`DEFAULT_RELEASE_DIR`) que les trois entrées — le CLI d'atelier, le contrôle de cohérence, le publieur — **importent** au lieu de la réécrire : sinon un défaut changé à un seul endroit désignerait un dossier et en nommerait un autre.

**Et l'atelier ne peut plus regrossir en silence, ni cacher 508 Mo.** Trois trous mesurés le 2026-09-13, tous les trois refermés. (1) **Rien ne lançait la purge** : `release:prune` n'existait que dans `package.json`, aucun workflow, aucun hook, et `check:release` nommait bien les installeurs étrangers mais sortait en **0** — donc le jour où personne ne se souvient de la commande, le dossier regrossit pendant qu'un contrôle vert regarde ailleurs. Le jugement est maintenant un **maillon de la chaîne qualité** (`npm run check:release:workshop`, `--check`) : dès qu'un fichier est **prouvé** redondant (le canal sert déjà ces octets exacts) il sort en **échec**, sans rien supprimer — l'acte reste humain. Il suit le précédent du gate d'audit : **hors ligne il se tait en le DISANT** (`WORKSHOP_SOFT_OFFLINE=1`, posé par le hook, pour qu'un commit ne dépende pas du réseau), alors que **la CI le lance strict** — un maillon qui ne peut pas échouer dans un contexte et le dit est un maillon honnête, un maillon vert-et-inerte ne l'est pas. Et le seul job de CI qui le lance n'est pas un cron mais **le job de publication** : c'est le SEUL runner où `release/` existe (le build vient d'y écrire), donc le seul endroit où un cron ne serait pas vert sans rien regarder — ailleurs l'atelier répond « non applicable, rien à juger », ce qui est honnête mais n'apprend rien. Là, strictement (aucune dérogation : un job qui publie ne peut pas déclarer l'atelier propre sans avoir lu le canal), et **après** le build — le juger avant ne regarderait que les restes de la veille. (2) **Les dossiers étaient invisibles à la règle** : `release/win-unpacked` pèse **508 Mo sur les 754 Mo restants** (67 %), et le plan ne le mentionnait pas — `check-release-coherence.mjs` ignore les dossiers à dessein, et un plan ne voyait que les fichiers qui portent un numéro. Un dossier n'a **pas d'empreinte** (c'est une sortie de build, pas un artefact livrable), donc il porte son **poids** et une raison, et il part par un acte **structurel** distinct (`--yes --unpacked`) : une preuve d'octets ne peut rien autoriser là où il n'y a pas un fichier livrable, et c'est dit dans ces mots. **Et tout le volume est attribué, pas seulement celui qu'on juge** : chaque entrée de surface reçoit **une** case (`à supprimer`, `conservés`, `nommés sans être jugés`, `hors sujet`, `ni fichier ni dossier`), chaque case affiche ses **octets**, et une dernière ligne confronte leur somme au dossier mesuré — `⚖️ volume : 753 Mo dans release/ — 246 Mo conservés (3) · 507 Mo nommés sans être jugés (2) · 6,4 Ko hors sujet (2)`. Deux volumes cessent ainsi d'être muets : les entrées « hors sujet » portaient un **nom sans taille** (un `latest.yml` de 361 octets et une archive oubliée de 400 Mo se lisaient pareil), et une entrée qui n'est **ni fichier ni dossier** (lien cassé, jonction) était silencieusement sautée — elle est désormais nommée, pesée, et comptée dans une case. Un volume invisible ne se remarque pas : il ne manque nulle part, il manque au total que personne ne fait.

**Et le dernier volume qui échappait à toute preuve en a maintenant une : un manifeste publié.** `release/win-unpacked` — **507 Mo**, 67 % de ce qui reste — n'a ni numéro ni empreinte : le canal ne pouvait donc rien dire de lui, et son sort restait une décision humaine. Or une arborescence se **décrit** : `npm run manifest:unpacked`, lancé par `electron:build` (donc jamais à la main — un manifeste écrit hier décrirait un arbre d'avant-hier), écrit `MamaTheraFinance-<version>-unpacked.manifest.json` — chemin, taille et sha256 de chaque fichier, **triés et normalisés**, pour que deux arbres identiques produisent deux fois les mêmes octets. Ce manifeste **voyage avec le lot** : le publieur le téléverse à côté de l'installeur, et le contrôle de cohérence exige qu'un release le porte. L'atelier recompose le sien et compare les **empreintes** : égales ⇒ le canal sert déjà ces octets-là, fichier par fichier, donc l'arborescence part sur le seul `--yes` — exactement comme un fichier dont le digest correspond, parce que c'est la même preuve. Quatre lectures, quatre sorts, et elles sont écrites ligne par ligne : un manifeste **publié d'une autre version** condamne ; celui de la **version en cours** ne condamne pas (c'est la sortie de build que les preuves locales lisent — même règle que pour les fichiers) ; un manifeste qui **ne décrit pas** cet arbre ne condamne rien (« jamais condamnée sur un doute ») ; et un dossier **illisible** (fichier verrouillé par l'application qui tourne) non plus — une preuve qu'on n'a pas pu faire ne condamne rien. Et la convention `-unpacked` reste **seule** à décider ce qui est une sortie de build : une preuve ne peut donc pas faire partir les ressources de build. Ce que ça coûte est dit plutôt que caché : hacher 507 Mo prend **~6 s** mesurées, donc l'atelier ne hache que quand une preuve est **possible** (un manifeste d'une autre version est publié — sinon le verdict ne pourrait pas changer, et c'est écrit), et le hook de commit s'en dispense explicitement (`WORKSHOP_TREE_PROOF=0`, dans son rapport : « preuve d'arborescence non tentée ») alors que le **job de publication de la CI la lance strictement**, sans aucune dispense.
 (3) **Le rappel de l'acte perdait son dossier** — le pire des trois, parce qu'il est le seul où être serviable est dangereux : mesuré live, le plan d'un `release-probe/` annonçait `Applique-le : npm run release:prune -- --yes --stale --unpublished`, c'est-à-dire la commande qui purge le **vrai** `release/`. `pruneCommand(plan)` est désormais le **seul** propriétaire de cette phrase : il déduit les drapeaux **et** `--dir` du plan, donc trois littéraux (dont un qui avait reçu le correctif et pas les autres) sont devenus un, et recopier le rappel agit sur le dossier qu'on vient de lire.

**Et `release-coherence.mjs` ne portait plus un métier mais cinq.** 727 lignes, treize exports : lire `latest.yml`, comparer local↔distant, juger la portée du canal, lire le frein d'urgence, décider une publication. Rien n'y était remplaçable séparément, et un mainteneur devait tout lire pour changer une comparaison. Découpé en quatre fichiers à un seul métier — `latest-yml.mjs` (lire les deux fichiers qu'un poste lit), `release-compare.mjs` (local↔distant), `release-reach.mjs` (à quoi le canal engage un poste), `release-version.mjs` (l'algèbre des numéros) — sans changer un seul verdict : les 135 cas de la suite passent sans être réécrits, et le lien d'immunité déclaré par le dépôt a suivi le module qui porte la preuve. Au passage, `compareVersions` existait **deux fois** avec deux sens différents : l'un rend `null` sur une version illisible, l'autre (`check-vercel-pins.mjs`) la lisait `0` — deux réponses à « A est-elle plus récente que B ». Il n'en reste qu'une, importée.

**Ce que la publication de la 1.0.4 a mesuré, et le dernier pas qui était resté à la main (depuis outillé).** Le piège des deux brouillons s'est reproduit à l'identique — un brouillon portant le blockmap, l'autre `latest.yml` + les deux exe (une passe par cible) — donc ils ont été **consolidés en un seul** avant promotion : le blockmap téléversé dans le brouillon complet, l'autre supprimé. C'était alors une main humaine sur l'API — **ce pas est depuis outillé** : c'est le publieur qui ouvre l'unique release, donc la consolidation n'est plus un geste manuel (voir ci-dessus). Puis la promotion (`draft=false`) — le seul geste qui rend une version **lisible** par `electron-updater` — et la vérification sur ce que les postes lisent vraiment : le flux Atom place `v1.0.4` en tête, le `latest.yml` **publié est identique au construit octet pour octet**, l'installeur se télécharge **sans aucun jeton** (HTTP 206, en-tête `MZ`), et l'empreinte est **rehachée depuis le dépôt public** — pas relue dans le dossier local. Sur le binaire empaqueté, les six passes d'`verify-updater.mjs` repassent (`PROOF_OK`), dont la passe « blocked » qui prouve la nouveauté de cette version : un poste que la porte bloque **écrit son journal** au lieu de rester muet.

**Et la 1.0.5, parce qu'un numéro publié ne peut pas changer de contenu.** Le trio « signalement d'un poste bloqué » (journal local, envoi au journal d'audit, puis file d'attente vidée au premier démarrage connecté) n'était pas dans le binaire installé. Reconstruire sous `1.0.4` n'aurait atteint **aucun poste** — `npm run check:release:tag` le refuse d'ailleurs en une ligne (« un même numéro ne peut pas changer de contenu : aucun poste ne verrait la différence. Montez la version. »), et c'est exactement la raison pour laquelle ce refus tombe *avant* tout téléversement. D'où une `1.0.5`, dont la vérification suit le chemin d'un poste, sans aucun jeton : le **brouillon** doit contenir tout ce qui est annoncé *et* être le seul pour ce tag (le piège des deux brouillons s'est reproduit à l'identique — `electron-builder` en ouvre un par cible, l'un portant le blockmap, l'autre `latest.yml` et les deux exe ; le mode `--draft` a nommé la répartition et refusé la promotion, les deux ont été consolidés) ; après promotion, le **flux publié** est rehaché depuis le dépôt public et le `latest.yml` servi est **identique au construit, octet pour octet** ; et le **canal** est relu comme le fait un poste (release publié le plus récent + frein lisible). Sur le binaire empaqueté, la passe `blocked` prouve deux choses au lieu d'une : le poste bloqué **écrit son journal**, et cette entrée est **en file** (`reportedAt` nul) — donc elle remontera au prochain démarrage connecté. Sans cette seconde exigence, la passe prouverait qu'un fait est inscrit sans prouver qu'il remontera un jour, c'est-à-dire précisément la moitié qui manquait.

**Un canal cassé est silencieux, donc il a son propre cron.** Les quatre premiers modes parlent de la version du `package.json` — donc d'un build local ; aucun ne répond à la question qui se pose le reste du temps : *un poste qui démarre voit-il encore quelque chose ?* Un release supprimé, un `latest.yml` illisible, un installeur disparu ou un frein corrompu ne font rougir aucun job, et personne ne l'apprend avant qu'un poste ne réclame. `.github/workflows/release-channel-watch.yml` (cron quotidien + `workflow_dispatch`, un push filtré quand le contrôle lui-même change, et — depuis qu'on l'a mesuré — **la publication elle-même** : `release: [published]` pour une publication hors chaîne, `workflow_run` sur le publieur pour la publication automatique, que `release` ne couvre pas puisque GitHub ne cascade aucun événement produit par `github.token`) lit donc le canal **tel qu'un poste le lit**, et **sans aucun jeton** — le mode `channel` ignore délibérément celui de l'environnement, parce qu'un canal qu'on ne sait relire qu'authentifié n'est pas prouvé pour un poste qui ne s'authentifie jamais. Et **la tête est demandée à l'endpoint que le poste interroge**, pas déduite par un tri maison : `electron-updater` demande `github.com/<owner>/<repo>/releases/latest` avec `Accept: application/json` et lit `tag_name` — un canal qui calcule sa propre tête (la plus récente par date de publication) juge un flux que personne ne lit, et les deux peuvent diverger en silence. La divergence est désormais **nommée** quand elle existe. Et le verdict ne porte plus sur la seule tête : **chaque version publiée est une population de postes**, donc chacune est jugée séparément — `deliveryReach` répond, version par version, ce qu'un poste resté là recevrait, exactement comme le client le décide (une tête **strictement supérieure** à ce qui tourne, sinon rien). Une version publiée PLUS HAUTE que la tête, ou une tête absente/illisible, sont donc **refusées** : la tête, elle, resterait parfaitement cohérente pendant qu'une population entière sortirait du chemin — c'est-à-dire le faux vert type. Une tête **retenue** par le frein est en revanche **nommée** sans être un refus : c'est le frein qui agit, et volontairement. Les pré-versions publiées ne portent aucun poste (le canal stable les ignore) mais sont **nommées** au lieu d'être tues — et elles ne sont plus **désignées** non plus : le tri « le plus récent publié » les exclut, exactement comme l'endpoint du poste les exclut. Sans ça, il désignait une version qu'aucun poste ne verra jamais, et la ligne de divergence reprochait au canal un désaccord qui venait de notre propre tri — mesuré le 2026-09-13 en publiant pour de vrai. Et la ligne qui affiche ce tri dit ce qu'elle montre (`le plus récent publié (notre tri)`) : y afficher la tête faisait se contredire deux lignes du même rapport. Quatre choses sont donc vérifiées, chacune pouvant manquer d'une façon différente : le release que le poste lit réellement (un brouillon est invisible pour l'updater — un brouillon plus récent est **nommé** sans être une faute, c'est une publication en cours), l'**empreinte de l'installeur rehachée depuis le dépôt public**, et le **frein d'urgence** (`updates/holds.json`) à l'URL exacte qu'un poste interroge à chaque vérification (`raw.githubusercontent.com/…/<branche>/updates/holds.json`, branche surchargeable par `--branch=` pour vérifier une branche de travail — ou pour **prouver le rouge**, une branche inexistante rendant le frein injoignable). Le frein a droit à son verdict séparé parce que sa panne est la plus silencieuse des trois : un fichier illisible ne retient rien, la mise à jour reste seulement *proposée*, et le dépôt reste vert — on s'aperçoit que le frein ne freine pas le jour où on compte sur lui. Sont donc **refusés** un frein vide ou absent, un JSON illisible, une racine qui n'est pas un objet, une liste `holds` absente, une entrée sans version ou avec une version qui ne peut correspondre à aucun release ; sont seulement **nommés** un motif absent (le frein tient quand même — « c'est le motif qui manque, pas le frein ») et une retenue en double.

**Et les octets sont lus par la voie du poste, parce que l'autre mentait.** `electron-updater` télécharge par `github.com/…/releases/download` (`browser_download_url`), pas par l'endpoint d'actif de l'API — lequel limite les requêtes **anonymes par adresse IP**, et un runner GitHub partage la sienne. Mesuré le 2026-09-13 sur le runner : `latest.yml absent du release v1.0.6`, alors que le fichier y était ; c'est la **lecture** qui échouait, et le verdict accusait le canal d'un défaut qui était le sien. Deux pannes qui se réparent différemment ne peuvent pas porter le même mot, donc les deux voies sont essayées, le statut de chacune est conservé (jamais jeté), une lecture par la seconde voie est **dite** — un repli silencieux serait un vert qu'on ne saurait pas expliquer — et un actif présent-mais-illisible se distingue d'un actif **absent**.

**Signature de code Windows** : le build signe automatiquement **tous** les artefacts (exe win-unpacked, `elevate.exe`, installeur NSIS + son désinstalleur, portable) dès que les variables standard sont définies : `CSC_LINK` (chemin/URL du `.pfx`) + `CSC_KEY_PASSWORD`. En CI, `.github/workflows/desktop-release.yml` (workflow_dispatch) restaure le certificat depuis les secrets `CSC_PFX_B64` + `CSC_KEY_PASSWORD`, signe et publie le GitHub Release (canal updater). ⚠️ SmartScreen n'est levé qu'avec un certificat d'une autorité de confiance (**OV/EV**) — un certificat auto-signé ne change rien à SmartScreen. Marche à suivre complète (achat, export `.pfx`, secrets CI) : [`docs/CODE_SIGNING.md`](docs/CODE_SIGNING.md). **Il existe une voie gratuite** : le dépôt est public et porte désormais une licence MIT, ce qui rend le projet recevable pour la **signature OSS gratuite** de la SignPath Foundation (certificats **EV**, reconnus immédiatement) — voir « §1 bis » du même document. Azure Trusted Signing, souvent cité comme la solution à 10 $/mois, est **écarté** : sa validation d'identité n'est pas ouverte aux organisations du Mali.

**Un certificat de test n'est pas une signature : c'est un parc figé — et c'est mesuré.** Le 2026-09-13, l'installeur que le canal servait (1.0.8, 129 081 184 octets, téléchargé depuis `/releases/latest`) était signé par le certificat **auto-signé de test**, et son `app-update.yml` — le contrat que le poste lit à chaque vérification — promettait `publisherName: [ "Mama Thera Finance (test)" ]`. `Get-AuthenticodeSignature` rendait `UnknownError` (« une chaîne de certificats a été traitée mais s'est terminée par un certificat racine qui n'est pas approuvé »). Or `electron-updater` n'accepte une mise à jour que si `Status -eq Valid` **et** si le sujet du certificat porte le nom promis (`NsisUpdater.js` → `windowsExecutableCodeSignatureVerifier.js`) ; sinon il lève `ERR_UPDATER_INVALID_SIGNATURE`. Autrement dit : **tout poste équipé de cette version refusait à jamais toutes les suivantes** — un parc figé, publié sous un workflow vert, et rien dans la chaîne ne le disait (le seul signal était un `::warning::` sur l'absence de certificat en CI). Le warning à l'installation n'était que le symptôme visible ; le défaut est le gel du parc.

**Le publieur refuse désormais d'envoyer un tel contrat sur le canal** (`npm run check:updater-trust`, appelé par `release:publish` **avant la première requête** — une fois un octet promu, aucune correction locale ne rattrape les postes équipés). Le contrôle lit le `app-update.yml` **réellement embarqué dans le binaire** (pas une intention de configuration), interroge Windows sur le **fichier réel**, et refuse quatre états, chacun adossé à une règle du poste : une liste de signataires **vide** (electron-updater ne peut satisfaire aucune liste vide), un nom de **test gravé** dans le contrat (refusé même si Windows le dit « Valid », parce qu'un certificat auto-signé n'est approuvé que sur la machine qui l'a créé), une **promesse sans signature** (le poste exige un signataire qui n'existe pas), et une chaîne **non approuvée** ou un sujet qui ne porte pas le nom promis. L'absence de promesse, elle, n'est **pas** un refus : c'est l'état d'un build non signé — le seul qui laisse le parc se mettre à jour tant qu'aucun certificat de confiance n'est posé — et le coût est **nommé** plutôt que tu (« Windows affichera « éditeur inconnu » à l'installation »). Et depuis le 2026-09-13, **un build non signé se publie** — décision explicite, pas un relâchement : signer avec un certificat de confiance reste le seul moyen de lever l'avertissement de Windows, mais refuser de publier sans certificat avait renvoyé la publication vers une machine locale, où un certificat de test a signé la 1.0.8 et **gelé le parc**. Un build sans `publisherName` promis, lui, laisse les postes se mettre à jour — y compris vers une future version signée — au prix du « éditeur inconnu » de Windows, que le publieur nomme et que la preuve d'action du job écrit en toutes lettres (« installeur NON signé »). Ce qui reste interdit, et refusé avant toute écriture sur le canal : signer avec un certificat **non approuvé**. Et **signer est devenu un choix explicite** : les secrets de certificat ne décident plus de rien à eux seuls, la signature s'active par la variable de dépôt `SIGNING_ENABLED=true`. Sans elle le runner restaure les secrets et ne les emploie **jamais**, en le disant (`certificat présent dans les secrets, signature ÉTEINTE`) — parce que c'est précisément un certificat de test *présent* qui a gravé la 1.0.8. Le verdict est **pur** (`scripts/lib/updater-trust.mjs`, 20 cas dans `tests/updater-trust.test.ts`) et le CLI **refuse de conclure hors Windows** : un contrôle qui ne peut pas mesurer est un contrôle absent, pas un contrôle satisfait. Vérifié sur les **vrais** octets du canal : le `app-update.yml` extrait de l'installeur publié et l'installeur lui-même, rejoués dans le contrôle, sortent en **1** en nommant les deux raisons — le signataire de test et la chaîne non approuvée, avec le motif de Windows mot pour mot. Pour lever le warning lui-même il faut un certificat **approuvé** (OV/EV, ou **Azure Trusted Signing** — `electron-builder` 26.15.3 porte `win.azureSignOptions` —, de l'ordre de 10 $/mois et sans achat d'OV), et les postes déjà équipés d'un build signé par le certificat de test **n'ont plus à être réinstallés** : leur contrat exige un signataire que plus aucune machine ne peut approuver, mais ce contrat est un **fichier chez eux** — `resources/app-update.yml`, relu par l'application elle-même à chaque démarrage. `npm run repair:frozen-updater -- --apply` y retire la promesse (sauvegarde `.bak`, relecture du fichier écrit pour le prouver), l'application redémarre, et le poste se remet à jour : pas de réinstallation, aucun droit administrateur, aucune donnée touchée. Le script est idempotent, il ne touche que les contrats de **cette** application, et il ne retire **que** ce qu'aucun certificat ne peut honorer — une promesse satisfiable est une garantie, donc laissée en place. `docs/CODE_SIGNING.md` §3 porte les trois lignes de code mesurées (dans la bibliothèque que le poste **exécute**) qui expliquent pourquoi ce fichier suffit.

Le **portable** ne se met pas à jour (pas de répertoire d'installation — désactivé à la détection de `PORTABLE_EXECUTABLE_FILE`). Preuve E2E du mécanisme (feed local, exe empaqueté) :

```bash
node scripts/verify-updater.mjs   # attend release/win-unpacked/MamaTheraFinance.exe
```

**Prérequis** : Windows 10/11 x64, internet pour Supabase. L'installeur installe dans le dossier utilisateur (pas d'administration requise).

## Structure

```
src/
  app/            # hooks métier (usePayments, usePayroll, useStudents…), mainViewsProps.ts
  components/     # vues + modales (AppModals, modales métier, ProductivityPanel…)
  lib/            # supabase client, PDF, offline queue, guards utilitaires
  i18n/           # translations.ts (fr/en)
  index.css       # design system (sections 1-5) + styles d'impression
  themes/         # midnight.css + overrides.css : les remaps !important par thème
supabase/
  migrations/     # migrations SQL ordonnées (schéma + RLS) ; FULL_SETUP_MIGRATION.sql généré
scripts/          # guards qualité (props, contraste, i18n, any, …) + lib/ partagée
tests/            # 70 suites node:test (788 tests)
```

`src/index.css` garde le design system (sections 1-5) et les styles d'impression ; les surcharges de thème `!important` vivent dans `src/themes/` (`midnight.css`, `overrides.css`), importées **dans cet ordre** juste après le design system — c'est l'ordre qu'elles avaient dans le fichier unique, et les seules règles non-`!important` du bloc battent leurs concurrentes par spécificité, pas par position. Le budget de 700 lignes par fichier ne tolérait `index.css` que le temps de la scission : l'entrée `ALLOWLIST` a été retirée dans le même commit. Les gardes qui lisent ces feuilles (sélecteurs CSS, modèle de contraste des tests) passent par le **corpus** — `src/index.css` plus les couches qu'il importe, résolu par `scripts/lib/theme-css.mjs` — jamais par un chemin en dur : c'est ce qui empêche un garde de devenir vert en ne contrôlant plus rien après un déplacement de règles.
